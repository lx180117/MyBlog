## 二、这次是怎么把数据库搭起来的

之前一直验不了，是因为本机**既没有 Docker，也没有安装版 PostgreSQL**，而且 `wsl` 里没有
任何发行版。可行路径只剩一条：用 PostgreSQL 官方 Windows 免安装二进制包。

| 步骤 | 做法 |
| --- | --- |
| 取二进制 | `postgresql-18.0-1-windows-x64-binaries.zip`，334MB，实测 1.6MB/s，约 205s |
| 解压位置 | `~/.workbuddy/binaries/pgsql/pgsql` |
| 数据目录 | `~/.workbuddy/binaries/pgsql/data`（`initdb --encoding=UTF8 --locale=C`） |
| 端口/账号 | **与 `server/.env` 里的 `DATABASE_URL` 完全一致**：`localhost:5432`、库 `blog`、用户 `blog` / `blog_password` |
| 认证 | 把 `pg_hba.conf` 的 host 规则从默认 `trust` 改成 `scram-sha-256`，确保是走密码校验而非「谁都能连」 |
| 建表 | `psql -f db/schema.sql` → **9 表 / 1 视图 / 13 触发器 / 39 索引**，`pg_trgm 1.6` 就位 |
| 种子 | `npm run db:seed` → 管理员 `admin` + 4 个分类 + 13 项站点配置 |

**没改 `.env` 里任何一行**，因为没有必要 —— 参数对齐就行。这样后续换到真实环境时不会出现
「本地能跑、线上配置不同」的偏差。

顺带把启停固化成脚本：`db/local-pg.sh`（`start` / `stop` / `status` / `psql` / `counts` /
`schema` / `seed`）。免安装包没有 Windows 服务，**重启电脑后数据库是停的**，用这个脚本拉起。

### 踩到的三个环境坑（都已写进脚本注释）

1. **`pg_ctl` 不认 Git Bash 的 `/c/...` 路径**。`$HOME` 在 Git Bash 下是 `/c/Users/lx`，直接当
   `-D` 参数传过去会报「目录不存在」，必须用 `cygpath -m` 转成 `C:/Users/lx/...`。
2. **在工具调用里 `pg_ctl start` 起来的进程会被连带回收**。日志显示服务已 ready，之后没有任何
   关闭记录进程就没了 —— 是被外部终止的。所以常驻运行要用后台任务方式直接跑 `postgres.exe`；
   用户在**自己的终端**里跑 `db/local-pg.sh start` 则不受影响。
3. **`psql -c` 里不要写中文**。Windows 控制台按 GBK 编码中文字面量，而客户端编码声明是 UTF8，
   服务端会直接报 `invalid byte sequence for encoding "UTF8": 0xbf`。查询语句保持纯 ASCII，
   中文只出现在数据里。

## 四、发现并修复的 5 个缺陷

前三个属于「静态检查根本查不出来、只有连上真库才会暴露」的一类；后两个属于
「只有把前端也跑起来、拿真实路由去对，才会暴露」的一类。

### 缺陷 1：Prisma 枚举类型名与 DDL 不一致，任何写 role/status 的操作全部失败

- **现象**：`npm run db:seed` 直接失败 —— `type "public.UserRole" does not exist`（PG 错误码 42704）。
- **根因**：`schema.prisma` 里表名都写了 `@@map("users")` 这类映射，但**四个枚举漏了**
  （`UserRole` / `UserStatus` / `ArticleStatus` / `CommentStatus`）。Prisma 于是去找
  `public.UserRole`，而 `db/schema.sql` 建的是 `user_role`。
- **影响面**：致命且隐蔽。注册、登录、发文、审核、评论、点赞——凡是涉及 `role` 或 `status`
  的读写都会报错。而它**在类型检查、openapi 导出、前端契约校验里都查不出来**，只有真连上库
  才会暴露。这也解释了为什么之前所有静态验证都是绿的。
- **修复**：给四个枚举补 `@@map`（保留数据库的 snake_case 命名风格，与表名映射保持一致），
  重新 `prisma generate`。修完顺手把活库结构与 schema 做了一次全量对比：9 个模型的字段与
  4 个枚举的取值**完全一致**，没有别的漂移。
- **回归**：场景 1 的注册/审核/发文链路即可覆盖。

### 缺陷 2：公开接口的「可选认证」给出一个缺 `id` 的用户对象

- **现象**：三处功能同时失效，看起来像三个不相干的 bug：
  1. 作者**看不到自己未发布的草稿** —— 详情接口返回 404（而「草稿仅作者与管理员可见」是需求里的功能点）；
  2. 详情页 `canEdit` 永远是 `false`，前端「编辑」入口永远不出现；
  3. **登录用户发表评论直接 500**。
- **根因**：`JwtAuthGuard` 在公开路由上为了「带令牌就顺带告诉前端我是谁」，自己做了一次
  `verifyAsync`，然后把 JWT 载荷原样赋给 `request.user`。而载荷里的用户标识字段是 **`sub`**，
  代码读的却是 **`id`**（受保护路由走 passport 策略，返回的对象是查库构造的，有 `id`，
  所以只有公开路由出问题）。
  第 3 条的链路最险：`user` 对象非空所以跳过了「游客必须填昵称」的校验，结果写出
  `user_id = NULL` **且** `nickname = NULL` 的评论，撞上 DDL 里「游客必有昵称」的 CHECK 约束，
  以未捕获异常收场 → 500。
- **修复**：
  - 根因：公开路由不再自己解令牌，改为调用 passport 策略解析一次，失败就静默降级为游客。
    顺带把「账号是否存在、是否被禁用」也纳入了校验（原来自己解令牌时是跳过的）。
  - 防御：评论服务改为用 `userId` 是否存在判断登录身份，而不是用 `user` 对象是否存在 ——
    即使上游再传进来半个用户对象，也不会写出违反约束的数据，而是给出明确的 400。
- **回归**：新增 3 条断言（作者预览草稿 200、`canEdit` 为 true、登录用户评论展示账号昵称）。

### 缺陷 3：非法路径参数返回 500 而不是 400

- **现象**：请求 `/api/v1/articles/abc/like` 返回 500，日志里是
  `SyntaxError: Cannot convert abc to a BigInt`。
- **根因**：控制器里直接写 `BigInt(id)`。它不是 `HttpException`，全局过滤器只能按未捕获异常
  处理，于是**明显的客户端错误返回了 500 并附带一整段错误堆栈** —— 可被用来刷日志。
- **影响面**：24 个带 `{id}` / `{articleId}` 的操作全部受影响（articles / articles-manage /
  comments / taxonomy / users 五个控制器）。
- **修复**：新增 `ParseBigIntPipe`，把参数转换从控制器里收进管道，非法 ID 稳定返回
  `400 无效的 ID：xxx`；24 处 `BigInt(id)` 全部改为直接用管道产出的大数。
- **回归**：新增 4 条断言（点赞 / 删除 / 彻底删除 / 发评论的非法 ID 均返回 400）。

### 缺陷 4：sitemap 与 RSS 里的链接全部指向不存在的路径（SEO 静默失效）

- **现象**：`sitemap.xml` 生成 `http://localhost:3001/article/欢迎来到这个博客`，
  但前端的真实路由是 `/articles/...`（复数）——请求这个地址是 404。
  分类与标签同理（后端写 `/category/`、`/tag/`，前端页面目录是 `categories`、`tags`）。
- **影响面**：sitemap 里 9 条 URL 有 7 条是死链，RSS 里每篇文章链接都是死链。
  搜索引擎据此收录 404 页面、RSS 读者点开是空页，**而且整个链路不报任何错**。
- **根因**：后端拼 SEO 链接时与前端路由各写各的，没有共同来源。这类问题在
  类型检查、OpenAPI 导出、前端契约校验里都看不见 —— 因为契约校验比的是**接口路径**，
  不是**页面路径**。
- **修复**：把前台路径收敛成 `feed.service.ts` 顶部的一处 `FRONT_ROUTES` 常量
  （并对分类/标签/作者也补上 `encodeURIComponent`），注释里写明必须与
  `client/app/pages` 的目录名保持一致。
- **回归**：新增 `npm run check:feed`（`server/scripts/check-feed-links.mjs`）——
  把 sitemap 里每个 `<loc>` 与 RSS 里每条文章链接**真的请求一遍**，全部要求 200。
  修复后 10 条链接全部可达；这一类漂移以后会被它挡住。

### 缺陷 5：首页标题出现重复的站点名

- **现象**：首页 `<title>` 是「我的博客 · 我的博客」。
- **根因**：`app.vue` 的 `titleTemplate` 统一拼 `· 站点名`，而首页自己又把标题设成了站点名。
- **修复**：模板改为「标题里已包含站点名就不再追加」，首页标题改为
  「站点名 · 副标题」→ 现在是「我的博客 · 技术、思考与记录」。
- **回归**：重新构建后在浏览器/抓取两端确认标题形态正确。

## 五、契约层面的变化（需要知悉）

修缺陷 3 时，控制器参数类型由 `string` 变成 `bigint`，Swagger 据此把**路径参数**的类型从
`string` 调整成了 `integer / int64`：

| 项 | 变化 |
| --- | --- |
| 路径数 / 操作数 / 模型数 | 52 / 61 / 59 —— **均无变化** |
| 路径参数 schema | 24 个操作由 `string` → `integer(int64)` |
| 前端影响 | 无。前端用模板字符串拼路径，且契约校验脚本比对的是归一化后的路径结构 |
| 已做的事 | 重新导出 `openapi.json`、重新生成 `app/types/api.ts`（59 模型）、前端 `npm run verify` 通过 |

之所以可以接受：URL 路径段在传输层本来就是字符串，而声明的 `int64` 更准确地反映了「这是
数据库 BIGINT 主键」。若希望严格保持「ID 一律用字符串收发」的文档口径，可以给这 24 处补
`@ApiParam({ type: String })` 改回 `string` —— 这只是文档表述，不影响运行时行为，等你决定。

## 六、顺手实测出的运维风险：`prisma db push` 会删掉全部搜索索引

`package.json` 里有 `prisma:push` 脚本，很容易被顺手当成「同步表结构」的工具用。实测了一次
（临时库先执行 `schema.sql`，再跑 `prisma db push --accept-data-loss`）：

| 对象 | push 前 | push 后 | 结果 |
| --- | --- | --- | --- |
| 表 | 9 | 9 | 不变 |
| 视图 | 1 | 1 | 保留 |
| 触发器 | 13 | 13 | 保留 |
| 索引 | 39 | **36** | 丢 3 个 |

被删的 23 个手写索引里，20 个被 Prisma 用自己命名的等价索引重建，剩下 3 个彻底消失且
不会补回 —— **恰好是全部搜索索引**：

- `idx_articles_search_vector`（tsvector GIN，英文全文检索）
- `idx_articles_title_trgm`（pg_trgm GIN，中文标题模糊搜索）
- `idx_articles_summary_trgm`（pg_trgm GIN，中文摘要模糊搜索）

即：在已有库上执行一次，中文搜索就退化成全表扫描，**过程中没有任何报错或警告**。
处理：在 `prisma/schema.prisma` 头部与 `server/README.md` 都写明了结论与实测数据；
表结构的唯一来源仍是 `db/schema.sql`（`db/local-pg.sh schema` 可重复执行，脚本本身幂等）。

## 七、不算缺陷、但需要知道的两个取舍

这两条是**故意**如此，如实记录而不是当 bug 修：

1. **refresh token 不轮换、不落黑名单**。同一个 refreshToken 可以反复使用，5 路并发刷新
   也全部成功。前端靠 `useApi` 的 inflight Promise 去重避免并发刷新，但**服务端无法主动
   吊销某一个会话**。如果哪天需要「异地登录挤下线」或「主动登出立即失效」，得引入
   refresh 白名单/黑名单表。
2. **改密码不会吊销已签发的令牌**。无状态 JWT + 每请求只校验账号状态，所以账号被盗后即使
   改了密码，攻击者手里的令牌在有效期内（access 15 分钟 / refresh 7 天）仍然可用。
   缓解做法是在用户表加一个 `token_version`（或 `password_changed_at`）参与校验，代价是
   每个请求多一次比对。

## 八、仍然没有验证的部分（如实说明）

| 项 | 原因 |
| --- | --- |
| 浏览器里的真实交互 | 无头环境下没跑真实点击；Element Plus 组件行为、表单校验提示、SSR 水合是否报 hydration mismatch 都还没在浏览器里看过 |

## 九、如何复现

```bash
# 1) 启动数据库（免安装二进制，无 Windows 服务，重启电脑后需要手动拉起）
bash db/local-pg.sh start
bash db/local-pg.sh counts        # users=1 articles=0 comments=0 tags=0 categories=4

# 2) 后端构建与启动
cd server
npm run build
node dist/main.js                              # 主实例 3000
```
