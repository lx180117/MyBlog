# 博客平台 · 云主机部署指南

> **这份文档是给谁看的**：假设你**从没部署过网站**，只写过代码、在本机跑过项目。

### 名词小词典

这些词在后面会出现很多次。先混个眼熟，不用背。

#### A. 电脑与网络

| 名词 | 通俗解释 | 类比 |
| --- | --- | --- |
| **云主机** | 在云服务商（阿里云、腾讯云、华为云…）那里**租**的一台电脑。它在别人的机房里，24 小时开着，有一个公网 IP，全世界都能访问到它。也叫 ECS / VPS / 服务器 | 租了一间远方的房子，随时能住 |
| **公网 IP** | 这台机器在全世界的"门牌号"，形如 `123.45.67.89` | 你家地址 |
| **域名** | 给人的地址，形如 `blog.example.com`。DNS 负责把它翻译成 IP | 给地址起个好记的名字 |
| **SSH** | Secure Shell，一种协议，让你**在自己的电脑上敲命令，去控制远方那台机器** | 远程遥控 |
| **命令行 / Shell / Bash** | 用打字代替点鼠标来操作电脑。Linux 服务器通常不装图形界面，只能靠它 | 用纸条下指令，而不是用手比划 |
| **端口 (port)** | 一台机器上有 65536 个"门"，每个程序占一扇门收发数据。网页服务默认走 **80**（HTTP）和 **443**（HTTPS） | 一栋楼里每个房间的房号 |
| **安全组 / 防火墙** | 云服务商的网络门禁，**默认关着所有门**。你要手动把 80 号门打开，外面才连得进来 | 小区的大门门禁 |
| **反向代理** | 站在最前面的"前台接待"。外面的人只知道接待员的地址，所有请求先给它，由它决定转给楼里哪个部门（前端？后端？） | 公司前台：访客找谁都得先经过前台 |

#### B. 打包与运行

| 名词 | 通俗解释 | 类比 |
| --- | --- | --- |
| **容器 (container)** | 一个**自带运行环境**的独立小盒子。里面跑着你的程序，还带着它需要的所有依赖（Node 版本、系统库…）。盒子之间互相隔离，不会打架 | 一个集装箱，里面已经装好了家具、水电、厨房，搬到哪都能立刻住 |
| **镜像 (image)** | 容器的"出厂模具"。你从镜像"启动"出一个容器。镜像是只读的，改不了；容器是可写的 | 做月饼的模子 |
| **Docker** | 制造和使用容器的那套工具 | 集装箱码头的整套设备 |
| **Dockerfile** | 一份**说明书**，写给 Docker 看：怎么一步步做出镜像（先装什么、再拷什么、最后跑什么命令） | 组装家具的图纸 |
| **Docker Compose** | 当你有**多个容器**要一起跑，用一份 YAML 文件描述它们的关系（谁先启动、谁连谁、共享什么目录）。一条命令全部拉起 | 一张"这顿饭要做哪几个菜、先炒哪个"的菜单 |
| **卷 (volume)** | Docker 管理的**持久化存储**。容器删掉重建，卷里的数据还在 | 房子拆了重盖，但保险柜能搬出来 |
| **多阶段构建** | Dockerfile 里写两段：第一段装一堆工具把程序**编译**出来，第二段只把编译结果拷过去。这样最终镜像更小 | 在工厂里造好零件，只把成品搬回家，不带机床 |

#### C. 网页是怎么跑起来的

| 名词 | 通俗解释 | 类比 |
| --- | --- | --- |
| **前端** | 用户看得见的部分（网页界面）。本项目的 `client/`，用 Nuxt（一个基于 Vue 的框架）写的 | 餐厅的大堂和菜单 |
| **后端** | 用户看不见的部分，负责处理数据、判断权限。本项目的 `server/`，用 NestJS 写的 | 餐厅的后厨 |
| **API** | 前后端约定的"对话方式"。前端按约定格式问，后端按约定格式答 | 点菜用的固定菜品编号 |
| **SSR** | Server-Side Rendering，服务端渲染。网页的 HTML 在**服务器上先拼好**再发给浏览器，而不是让浏览器自己拼。好处：爬虫能抓到内容（利于搜索引擎收录）、首屏快 | 餐厅把菜做好端上来，而不是把生肉和炉子送到桌上让客人自己炒 |
| **CSR** | Client-Side Rendering，客户端渲染。浏览器拿到一个空壳，再自己去要数据、拼页面 | 客人自己炒 |
| **CORS** | 浏览器的安全规则：A 网站页面里的 JS 默认**不许**去请求 B 网站的接口，除非 B 明确说"我允许 A" | 跨部门办事需要介绍信 |
| **Nginx** | 一个非常常用的网页服务器软件。本项目里它当前台（反向代理）+ 直接发图片文件 | 前台接待员 + 收发室 |
| **sitemap / RSS** | sitemap 是给搜索引擎看的"本店所有页面清单"；RSS 是给读者订阅用的"最新文章推送" | 给导游的地图 / 给订户的报纸 |
| **canonical** | HTML 里的一行标记，告诉搜索引擎"这个页面的正式地址是它"，避免同一个内容被当成多个页面 | 给一份文件标注"以此版本为准" |

#### D. 数据

| 名词 | 通俗解释 | 类比 |
| --- | --- | --- |
| **数据库** | 专门用来**存数据**的软件。本项目的 `PostgreSQL`（简称 PG），存文章、用户、评论 | 图书馆的书库 |
| **表 (table)** | 数据库里的一张"表格"，有固定的列。本项目有 9 张表（用户表、文章表、评论表…） | Excel 里的一个工作表 |
| **DDL / schema** | Data Definition Language，"定义数据结构"的 SQL 语句。本项目的 `db/schema.sql` 就是它 | 图书馆的排架规则说明书 |
| **seed（种子数据）** | 系统第一次跑起来时需要的**初始数据**，比如管理员账号、默认分类 | 搬新家先买好米和盐 |
| **索引 (index)** | 让查询变快的"目录"。没有索引时数据库要一行行翻（全表扫描），有了就能直接定位 | 书的目录页 |
| **触发器 (trigger)** | 数据库里的"自动反应"：满足条件时自动执行一段逻辑。本项目用它自动维护点赞数、评论数 | 门被推开时自动响的铃 |
| **pg_dump** | PostgreSQL 自带的**备份**工具，把整个库导出成一个 `.sql` 文件 | 把图书馆的目录和内容全部复印一份 |
| **psql** | PostgreSQL 自带的**命令行客户端**，用来连上数据库敲 SQL | 进图书馆查书的窗口 |

#### E. 安全

| 名词 | 通俗解释 | 类比 |
| --- | --- | --- |
| **环境变量** | 程序启动时从外部读入的配置，比如数据库密码。好处是**代码和配置分开**：同一份代码，换个配置就能跑在不同环境 | 电器用插座取电，而不是把电线焊死在墙里 |
| **`.env` 文件** | 把一堆环境变量写在文件里的地方。**这个文件绝对不要提交到代码仓库** | 家里的保险箱，不外借 |
| **HTTPS** | HTTP 的加密版。传输的内容被加密，中途被人截获也看不懂 | 用密封信封寄信，而不是明信片 |
| **证书 / Let's Encrypt / certbot** | HTTPS 需要一张"身份证书"证明"这个域名确实是你的"。Let's Encrypt 是免费发证书的机构，certbot 是自动申请的软件 | 官方盖章的营业执照 |
| **JWT** | 一种"电子门禁卡"。用户登录后服务器发给他一张字符串，之后每次请求带着它，服务器就知道"这是谁" | 办完手续发的出入证 |
| **密钥 (secret)** | 用来签发票据的"私章"。**泄露了，别人就能伪造出入证** | 公章 |
| **限流** | 限制某个来源在单位时间内能请求多少次，防止有人写脚本疯狂刷接口 | 排队取号，一人一次拿一个 |

## 一、部署前必须理解的三件事

这三件事想清楚了，后面遇到问题会好定位很多。

### 整体结构：一次网页请求的旅程

用户打开你的博客时，背后发生了什么：

```
                    用户的浏览器
                         │  ① 访问 http://blog.example.com
                         ▼
        ┌────────────────────────────────────────┐
        │  nginx 容器（唯一对公网开门的容器，监听 80） │  ② 看请求路径决定转给谁
        └────────────────────────────────────────┘
             │                    │                    │
    /api/v1/...         /uploads/xxx.jpg          其他所有路径
             │                    │                    │
             ▼                    ▼                    ▼
    ┌─────────────┐      ┌─────────────┐      ┌────────────────┐
    │  api 容器    │      │ 图片文件     │      │  client 容器    │
    │ (NestJS)    │      │ 直接从磁盘发 │      │ (Nuxt SSR)     │
    └─────────────┘      └─────────────┘      └────────────────┘
             │                                         │
             ▼                                         │ ③ SSR 渲染页面时
    ┌─────────────────┐                               │   也要问后端要数据
    │ postgres 容器    │ ◄─────────────────────────────┘
    │  (PostgreSQL)   │
    └─────────────────┘
```

**三个关键点**（记住这三个，排错就有方向）：

1. **只有 `nginx` 这一个容器的端口对公网开放**。用户永远只能敲到 nginx 的门，
   由它决定转给谁。其他三个容器都躲在内部网络里，外面够不着——这样攻击面最小。
2. **只有 `nginx` 一个"门牌号"**。前端、后端、图片全都通过同一个域名访问
   （`/` 是前端、`/api/` 是后端、`/uploads/` 是图片）。这叫**同源部署**，
   好处是浏览器不会因为 CORS 规则拦截请求。
3. **`postgres` 的数据存在"卷"里**。容器可以被删掉重建（更新代码时就会这样），
   但卷里的数据保留，所以你的文章不会丢。

### 第 1 件：本次部署补齐了哪些东西

在你看这份文档之前，仓库里原有的编排**有两个会导致部署失败的缺口**，现已补齐：

| 原来的缺口 | 会造成什么后果 | 现在的做法 |
| --- | --- | --- |
| **前端没有 Dockerfile** | 编排里根本没有前端服务。容器全部启动成功、状态全是绿的，但打开站点只有 404 ——因为 `client/` 目录从来没被构建过 | 新增 `client/Dockerfile`（多阶段构建，运行阶段只留 `.output`） |
| **Nginx 把 `/` 转发到 `host.docker.internal:3001`** | `host.docker.internal` 这个名字只有 Docker Desktop（Mac/Windows 上的桌面版）才提供，**Linux 云主机默认解析不了** → 首页直接 502。这是最坑的一种：在本机测试完全正常，一上云就挂 | 改为转发到编排内的 `client` 服务（走容器网络的服务名） |

> 这不是"需求变更"，而是**只有真正要部署时才会暴露的缺陷**。本机没有 Docker，
> 所以之前一直是"看起来齐了"。这也是为什么第十二节要把"哪些没实测过"写得那么清楚。

### 第 2 件：浏览器和 SSR 用的 API 地址**必须**不一样

这是全篇最容易踩、症状又最迷惑的一个点。**请至少把这一段读完。**

前端在两种不同的环境里跑，需要两个不同的后端地址：

**情况 A：代码在浏览器里跑**（用户点了按钮，JS 发请求）

- 应该请求 `/api/v1/articles` —— 一个**相对路径**，没有写域名。
- 浏览器会自动补成"当前网站的域名 + /api/v1/articles"，然后由 nginx 转发给后端。
- 好处 ①：不需要 CORS（同源）。
- 好处 ②：**域名没有写死进构建产物**，以后换域名，不用重新构建镜像。

**情况 B：代码在服务器上跑**（SSR 渲染页面时，Node 进程里发请求）

- 这时如果也写 `/api/v1/articles`，会直接报错 `Failed to parse URL`。
- 原因：浏览器知道"当前网站的域名"是什么，**但 Node 进程不知道**。
  对一个相对路径，它连"往哪发"都判断不出来。
- 所以服务端必须给一个**绝对地址**。

因此用了**两个**环境变量（`docker-compose.yml` 里已经配好，你不用改）：

| 变量 | 值 | 谁在用 | 为什么是这个值 |
| --- | --- | --- | --- |
| `NUXT_PUBLIC_API_BASE` | `/api/v1` | 浏览器 | `PUBLIC` 表示会下发到浏览器；相对路径，免 CORS |
| `NUXT_API_BASE_SERVER` | `http://api:3000/api/v1` | 仅 SSR | 没有 `PUBLIC` 前缀，**不会**下发到浏览器（私有）；`api` 是容器服务名 |

> **为什么用 `http://api:3000` 而不是公网域名？**
> 因为 docker compose 会自动给每个容器分配一个内部域名，名字就是服务名。
> 容器之间用这个内部地址通信，比"绕出去再绕回来访问自己的公网地址"稳定得多
> （后者一旦 DNS 或安全组有问题就断）。这也是 docker compose 最实用的功能之一。

### 第 3 件：站点地址只改一处 —— `SITE_URL`

`server/.env` 里的 `SITE_URL` 是**你这个博客对外的地址**。编排文件会用它自动推导出另外四项：

| 推导出来的变量 | 用途 |
| --- | --- |
| 后端的 `SITE_BASE_URL` | sitemap 和 RSS 里生成的**绝对链接** |
| 后端的 `UPLOAD_BASE_URL` | 上传图片的对外前缀 |
| 后端的 `CORS_ORIGINS` | 允许哪些来源跨域访问接口 |
| 前端的 `NUXT_PUBLIC_SITE_URL` | 页面的 canonical、`og:url`、分享链接 |

**如果没设置，`docker compose up` 会直接报错退出。** 这是故意设计的。

> **为什么不给个默认值、让它"能跑就行"？**
> 因为漏设的症状是：**站点表面上完全正常，但 sitemap、canonical、图片链接全部指向 `localhost`**。
> 你自己用浏览器打开首页，看不出任何问题；只有搜索引擎爬虫抓到的是一堆无效地址，
> 而这类故障通常几周后才被发现，排查起来毫无头绪。
> 与其留一个"能跑但暗中有病"的默认值，不如让它在启动时就大声报错。

**填写规则**：

```bash
# 只有 IP、还没域名（先能用起来）
SITE_URL="http://123.45.67.89"

# 有域名、配好 HTTPS（推荐；证书流程见第九节）
SITE_URL="https://blog.example.com"
```

⚠️ **末尾不要带斜杠**。写 `https://blog.example.com`，不要写 `https://blog.example.com/`。

## 二、准备主机与工具

### 2.1 需要什么配置

| 项目 | 要求 | 为什么 |
| --- | --- | --- |
| **CPU / 内存** | **2 核 2G 起**（1 核 2G 也能跑，但构建时容易卡死） | 四个容器常驻约占 800MB～1.2GB；**构建镜像时是峰值**，需要额外内存 |
| **硬盘** | 40GB 起 | 系统 + 镜像（约 1.5GB）+ 数据库 + 你上传的图片 |
| **操作系统** | Ubuntu 22.04 / 24.04 或 Debian 12 等主流 x86_64 发行版 | 文档里的命令以 Ubuntu 为准；其他发行版装 Docker 的方式可能略有差别 |
| **Docker** | **24 以上，且带 compose v2** | 具体要求见下 |
| **安全组** | 放行 **80**（配 HTTPS 后还要 **443**） | 不放行的话，外面永远连不上 |
| **域名** | 可选，但**强烈建议** | 没有域名就没法配 HTTPS；而且 IP 一旦变化链接全失效 |

### 2.2 关于 Docker 版本：`docker compose` 与 `docker-compose` 的区别

这两个命令**长得几乎一样，但不是同一个东西**，很多教程混着写，很容易踩坑：

| 命令 | 是什么 | 状态 |
| --- | --- | --- |
| `docker compose`（中间是**空格**） | **compose v2**，已经集成进 Docker 命令行，是一个插件 | ✅ 现在用这个 |
| `docker-compose`（中间是**连字符**） | **compose v1**，独立的 Python 程序 | ❌ 已停止维护 |

本项目的 `docker-compose.yml` 用的是 v2 的写法（特别是 `depends_on` 里的
`condition: service_healthy`，v1 不支持），**所以必须用 v2**。

装好后用这条命令确认：

```bash
docker compose version
# 期望输出形如：Docker Compose version v2.x.x
```

如果提示 `docker: 'compose' is not a docker command`，说明是旧版本，请按第四节重装。

### 2.3 关于端口暴露面：为什么只开 80

打开 `docker-compose.yml` 你会看到，只有 nginx 用了 `'80:80'` 这种写法（对公网开放），
另外几个是：

```yaml
ports:
  - '127.0.0.1:3000:3000'    # api：只有主机自己连得上
```

**`127.0.0.1:` 这个前缀的意思是"只绑定本机回环地址"**——外面的人连不上，
但你自己 SSH 登录到主机后可以 `curl 127.0.0.1:3000/health` 来排查问题。
`postgres` 更彻底，连映射都没写，只在容器网络内可达。

> **为什么这么讲究？** 每一次对外开放的端口都是被扫描器盯上的机会。
> 数据库端口暴露在公网是**极常见**的失陷原因（弱密码 + 公网可达 = 数据被拖走）。
> 少一个端口就少一个风险点。

### 2.4 你的电脑上要有什么

- **一个能敲命令的终端**。Windows 上推荐用 **Git Bash**（装 Git 时自带），
  或者 Windows 10+ 自带的 PowerShell。本项目的开发环境就是 Git Bash。
- **`ssh`、`scp`、`tar`**，用来登录主机和把代码传过去。这三个 Git Bash **自带**。
- 如果主机是全新装的，你还得知道**怎么用 SSH 登录它**（云服务商的控制台通常会给一段登录命令）。

> ### ⚠️ 一个很多人踩过的坑：Git Bash **没有** rsync
>
> 网上讲部署的文章几乎都用 `rsync` 传代码，因为它能"只传有变化的部分"。
> **但 `rsync` 不是 Git Bash 自带的**——它是独立的软件，Windows 上要额外安装
> （而且装起来比 Linux 麻烦）。
>
> 如果你照着别的教程敲 `rsync` 却报 `command not found`，不是你敲错了，
> 是这台机器上真的没有。
>
> **本文档因此不用 rsync**，改用 `tar + ssh` 的组合——用的是 Git Bash 自带的工具，
> 开箱即用，效果一样好（第三节会讲原理）。

> ### 💡 名词小课堂：SSH 怎么用
>
> 最常见的形式：
>
> ```bash
> ssh root@123.45.67.89
> ```
>
> 读法：以 `root` 这个用户的身份，登录到 `123.45.67.89` 这台机器。
> 第一次连接会问 `Are you sure you want to continue connecting?` —— 输入 `yes` 回车。
> 然后要密码（有可能你第一次是在云控制台重置的密码）。
>
> **登录成功后的特征**：命令提示符会从你本机的东西变成类似 `root@iZxxx:~#`。
> **此时你敲的每条命令，都作用在远方那台服务器上，不是你的电脑。**
> 这是新手最容易搞混的地方——所以在本文档里，我会明确标注每条命令
> 是在"**本机**"还是"**主机上**"执行。
>
> 退出登录：输入 `exit` 回车。

## 三、把代码送到主机

### 3.1 先看清现实：不能整个目录拷过去

本项目当前**不是 git 仓库**，所以不能用 `git clone` 把代码拉到服务器上。
只能用"文件传输"的办法。

但直接拷整个项目目录会是一场灾难。这是本机实测的两组数字：

| 传法 | 文件数 | 体积 |
| --- | --- | --- |
| 整个目录无脑全传 | **56,613 个** | 几百 MB，慢到你会以为程序卡死了 |
| 排除构建产物与依赖后 | **237 个** | **416 KB** |

差了 **268 倍**。罪魁祸首是 `node_modules` 和 `.output` / `dist` 这类**构建产物**：

- `node_modules` 装着项目用到的所有第三方库。前后端加起来几十万个文件，
  而服务器上的容器**会自己重新装一份**，传过去纯粹是浪费时间和流量。
- `.output` / `.nuxt` / `dist` 是本机（Windows）编译出来的结果。
  它们**和操作系统绑定**——Windows 上编出来的东西拿到 Linux 上不一定能用，
  而且容器里会重新编译。传过去不但没用，还可能引起莫名其妙的报错。
- `.env` 里装着密码和密钥，**绝对不能出门**。

所以"传代码"这件事的技术难点不在"怎么传"，而在**"怎么把不该传的挡在外面"**。

### 3.2 用什么传：`tar + ssh` 管道（而不是 rsync）

> ### 💡 名词小课堂：为什么不用 rsync？
>
> 网上讲部署的文章几乎都用 `rsync`，它的招牌功能是**增量同步**——
> 第二次传的时候只传改过的文件。听起来很棒，但有两个现实问题：
>
> 1. **`rsync` 不是 Git Bash 自带的**（很多人以为自带，其实没有）。
>    Windows 上装它要额外折腾，对新手不划算。
> 2. 我们这个项目**每次更新也就几百 KB**，就算全量传也不到一秒钟，
>    增量同步省下的那点时间根本感觉不到。
>
> 结论：用 **Git Bash 自带的** `ssh` + `tar` 就够，而且更好理解。

> ### 💡 名词小课堂：`tar` 和"管道"是什么
>
> **`tar`** 是 Linux 世界最经典的打包工具。它把一堆文件合成**一个文件**，
> 方便整体搬运——可以理解成"把散装行李装进一个箱子"。
> 名字来自 **t**ape **ar**chive（磁带归档），是 1970 年代为磁带备份发明的，
> 一直用到现在。
>
> 常见的三个参数：
>
> | 参数 | 含义 | 记忆法 |
> | --- | --- | --- |
> | `c` | create，创建包 | **c**reate |
> | `x` | extract，解开包 | e**x**tract |
> | `t` | list，只看内容不解开 | lis**t** |
> | `z` | 用 gzip 压缩 | **z**ip |
> | `f` | 后面跟着文件名 | **f**ile |
>
> 所以 `tar czf 包名 目录` 是"打包"，`tar xzf 包名` 是"解包"。
>
> **管道 `|`** 则是把前一个命令的输出，直接当作后一个命令的输入——
> 像接水管一样把两个命令串起来。本文档里它长这样：
>
> ```bash
> tar czf - . | ssh 服务器 'tar xzf - -C /opt/blog'
> #   ↑ 打包           ↑ 把打包结果送过去，并在那边解开
> ```
>
> 注意那个 `-`（连字符）：它表示"**不存成文件，直接输出到管道**"。
> 这一步的意义是——**中间那个压缩包从不在任何一台机器上落盘**，
> 打完立刻经网络流过、在服务器上解开就没了。
> 所以哪怕项目里有敏感文件，也不会在磁盘上留下一份临时副本。

这条路只有三步：**配免密 → 传 → 验证**。下面依次讲。

### 3.3 第一步：配置免密登录（只需做一次）

**为什么必须先做这一步？** 因为传输命令里 `tar` 的输出是通过管道喂给 `ssh` 的。
一旦管道接上，`ssh` 就**没法再从键盘读你的密码**了（键盘输入已经被管道占用），
它只能靠密钥认证。所以不配免密，传输会直接失败或卡住不动。

好消息是：你本机**已经有密钥**了（我检查过 `~/.ssh/id_ed25519`，2024 年 12 月生成的，
可以直接用）。现在只差把**公钥**装到服务器上。

> ### 💡 名词小课堂：密钥登录的原理
>
> SSH 除了"账号 + 密码"，还支持一种更安全也更方便的登录方式：**密钥对**。
>
> - 生成时会得到**两个文件**：`id_ed25519`（私钥）和 `id_ed25519.pub`（公钥）
> - **公钥像一把锁**，可以随便复制、发给任何服务器，被人看到也没关系
> - **私钥是唯一的钥匙**，永远留在你自己的电脑上，**绝不能发给任何人**
> - 登录时，服务器拿你之前放上去的"锁"出一道题，只有持有"钥匙"的人能答对
>
> 好处：① **偷密码的套路全失效**（没有密码可偷）；② 不用每次输密码。
> 云服务器厂商几乎都推荐这么做。

在**本机**（Git Bash）执行，把公钥装到服务器上：

```bash
ssh-copy-id root@你的服务器IP
```

例如你的服务器是 `172.40.3.224`，就写 `ssh-copy-id root@172.40.3.224`。

> ⚠️ **这一步会要求你输入一次服务器的密码**（这是最后一次输密码）。
> 输入时**屏幕上不会显示任何字符**——不是键盘坏了，这是 Linux 的安全设计
> （防止旁人从屏幕长度猜出密码有几位）。盲打输入后直接回车即可。

> 💡 `ssh-copy-id` 的名字读作 "copy id"，意思是"把身份（公钥）拷过去"。
> 如果它提示 `command not found`，说明你的 Git Bash 版本比较老，
> 可以手工完成同一件事：
>
> ```bash
> cat ~/.ssh/id_ed25519.pub | ssh root@你的服务器IP \
>   "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
> ```

装完后**验证一下**是不是真的免密了：

```bash
ssh root@你的服务器IP 'echo 免密登录成功，主机名是 $(hostname)'
```

如果**没有**再让你输密码，直接打印出结果，就说明配好了。
如果还是问密码，说明公钥没装上，回头检查上一步的报错。

### 3.4 第二步：执行传输

**先定义三个变量**，把"要改的信息"全部集中在这里——后面的命令直接用，
不用再反复替换。在**本机**执行：

```bash
# ↓↓↓ 只改这三行，其余命令照抄即可 ↓↓↓
SERVER=172.40.3.224                              # 你服务器的 IP 或域名
LOCAL=/c/Users/lx/WorkBuddy/2026-09-17-17-12-31  # 本机项目路径（Git Bash 写法）
REMOTE=/opt/blog                                 # 服务器上存放代码的目录
```

> 💡 **这是你在全文里唯一需要动脑替换的地方。**
> 变量只对**当前这一个终端窗口**有效——如果关掉窗口再回来，
> 重新跑这三行就行（这是新手最常遇到的"为什么我的命令突然找不到变量了"）。

然后执行传输（**本机**）：

```bash
cd "$LOCAL"

tar czf - \
  --exclude='node_modules' \
  --exclude='.output' \
  --exclude='.nuxt' \
  --exclude='dist' \
  --exclude='.env' \
  --exclude='.workbuddy' \
  . | ssh root@$SERVER "mkdir -p $REMOTE && tar xzf - -C $REMOTE"
```

**逐段拆解这条命令**（它看起来吓人，其实只有两半）：

| 片段 | 作用 |
| --- | --- |
| `cd "$LOCAL"` | 先切到项目根目录。**必须切**，否则后面 `.` 打包的是你当前所在的任意目录 |
| `tar czf -` | 把当前目录打包压缩。`-` 表示输出到管道、不落盘 |
| `--exclude='xxx'` | 排除规则（见下表）。这是整条命令里**最重要的部分** |
| `\|` | 把包"流"给后一个命令 |
| `ssh root@$SERVER "..."` | 连到服务器并执行引号里的命令 |
| `mkdir -p $REMOTE` | 在服务器上建好目标目录（`-p` 表示"不存在就建、已存在不报错"） |
| `tar xzf - -C $REMOTE` | 从管道读取包并在 `$REMOTE` 里解开（`-C` 指定解到哪个目录） |

**每一项排除的原因**（这几行不是可有可无的）：

| 排除项 | 为什么必须排除 |
| --- | --- |
| `node_modules` | 前后端加起来**几十万个文件**。传上去要几个小时，而且容器里会重新安装一份。**这是最大的一坑** |
| `.output` / `.nuxt` / `dist` | 本机构建的产物。容器内会重新构建，传了也白传，还可能因平台不同（Windows/Linux）而出错 |
| `.env` | **里面是密钥**。绝不能离开你的电脑；服务器上单独创建（第五节）。它同时也被 `.gitignore` 排除 |
| `.workbuddy` | 是 AI 助手的工作记录目录，和程序运行无关，传上去只会让人困惑 |

> ⚠️ **绝对不要用尖括号 `<>`！**
> 你可能在别的教程里见过 `root@<你的IP>` 这种写法——
> 其中的 `<>` 是**"请替换这里"的示意符号，不是要你敲的字符**。
> 如果照着敲，`bash` 会把 `<` 理解成"重定向"，
> 你会得到一句莫名其妙的报错：
>
> ```
> bash: 172.40.3.224: No such file or directory
> ```
>
> 这句话的真实意思是"**我想从名为 `172.40.3.224` 的文件里读输入，但找不到这个文件**"——
> 和你真正想做的事（连服务器）毫无关系。
> 本文档里的命令都**不含尖括号**，可以直接复制粘贴。

> ### ⚠️ 另一个 Windows 特有的坑：路径要写成 `/c/...` 而不是 `C:/...`
>
> 在 Git Bash 里，`C:\Users\lx` 和 `C:/Users/lx` **对大部分命令都能用**，
> 但对 `tar` 有个例外——**`tar` 会把 `C:` 当成"远程主机名"**！
>
> 因为 `tar` 有一条老语法：`tar czf 主机名:路径` 表示"打包到另一台机器上"
> （当年为磁带服务器设计的）。所以当你写：
>
> ```bash
> tar czf C:/Users/lx/backup.tgz .        # ✗ 会失败
> ```
>
> 它会以为你要连一台名叫 `C` 的机器，然后报出这句荒唐的错：
>
> ```
> tar (child): Cannot connect to C: resolve failed
> ```
>
> **正确写法是用 MSYS 风格：`/c/Users/lx/backup.tgz`**（盘符小写、前面加斜杠）：
>
> ```bash
> tar czf /c/Users/lx/backup.tgz .        # ✓ 正常
> ```
>
> 好消息：本文档 3.4 节的**主传输命令不涉及这个问题**——
> 因为它是"输出到管道"，中间根本没有出现文件路径。
> 只有 3.6 节那个 `scp` 备选方案需要你自己指定文件位置，那里务必用 `/c/...` 写法。

### 3.5 第三步：验证传上去了什么

传输没有输出是正常的（说明没出错）。**但要亲眼确认一次**，在**本机**执行：

```bash
ssh root@$SERVER "cd $REMOTE && echo '--- 顶层目录 ---' && ls -a && echo '--- 文件总数 ---' && find . -type f | wc -l && echo '--- 关键文件是否都在 ---' && ls -l server/docker-compose.yml server/Dockerfile client/Dockerfile db/schema.sql"
```

期望看到：

- 顶层有 `client` `db` `docs` `server` 四个目录，**没有** `node_modules`
- 文件总数在 **200 多**（如果看到上万，说明排除规则没生效，检查上一节命令有没有抄漏 `--exclude`）
- 四个关键文件都列出且大小不为 0

如果对不上，**先别往下走**——第三节之后的每一步都建立在这份代码上。

### 3.6 万一还是想用 scp

`scp` 也能用（Git Bash 自带），但它**只能整个目录拷，没法优雅地排除**，
所以更现实的做法是先在本机打包好，再传单个文件：

```bash
# 本机：先按 3.4 的方式打个包（这次存成文件而不是走管道）
cd "$LOCAL"
tar czf ~/deploy.tgz \
  --exclude='node_modules' --exclude='.output' --exclude='.nuxt' \
  --exclude='dist' --exclude='.env' --exclude='.workbuddy' .

# 本机：传这个包
scp ~/deploy.tgz root@$SERVER:/tmp/

# 服务器上：解包
mkdir -p /opt/blog && tar xzf /tmp/deploy.tgz -C /opt/blog && rm /tmp/deploy.tgz
```

> 💡 **这里用 `~` 表示"我的用户主目录"**，在 Git Bash 里它会自动展开成
> `/c/Users/你的用户名`。用 `~` 而不是写全路径，好处是**完全避开了上一节说的
> `C:` 被当成主机名的问题**，而且换电脑也不用改。

> 💡 先 `tar` 再 `scp`，比直接 `scp -r` 好的地方有两点：
> 一是能精确控制排除哪些目录；二是传的是**一个文件**，
> 比传几百个零散文件快得多，中途断线也更容易判断进度（用 `scp -v`）。
>
> 代价是多占一步磁盘（本机有个 416 KB 的临时包），传完记得删掉。

## 四、安装 Docker

### 4.1 在主机上执行

SSH 登录到主机后，执行官方一键安装脚本：

```bash
curl -fsSL https://get.docker.com | sh
```

> ### 💡 名词小课堂：`curl ... | sh` 是什么意思
>
> 拆成两半看：
>
> - **`curl -fsSL https://get.docker.com`**：下载这个网址的内容（一段安装脚本），
>   并打印到屏幕上。
>   - `-f` 遇到 HTTP 错误（如 404）就直接失败，不把错误页面当成脚本
>   - `-s` 不显示进度条
>   - `-S` 但出错时仍然显示错误信息
>   - `-L` 跟随重定向（这个网址会跳转）
> - **`| sh`**：把前一个命令的**输出**，当成后一个命令的**输入**。
>   所以整句的意思是"下载一段脚本，交给 sh（shell）去执行"。
>
> ⚠️ **安全提醒**：这种"下载别人的脚本直接执行"的做法，本质上是
> **把 root 权限完全托付给那个网址**。Docker 官方脚本是可信的，
> 但在别的场合遇到 `curl | sh` 时要多留个心眼——**先下载下来读一遍再执行**：
>
> ```bash
> curl -fsSL https://get.docker.com -o get-docker.sh
> less get-docker.sh        # 读一读（按 q 退出）
> sh get-docker.sh          # 确认没问题再跑
> ```

> ### ⚠️ 实测提醒：官方脚本在国内可能时通时断
>
> 2026-09-20 在一台国内主机上实测：官方脚本要访问的 `download.docker.com`
> **三次测试出现「200 → 000 → 200」的抖动**，也就是时通时断。这种情况
> `curl | sh` 可能中途失败、或者卡很久。
>
> **更稳的做法是改用国内源的软件仓库**（下面以阿里云为例，Rocky / RHEL / CentOS 系适用，
> 实测约 3 分钟装完）：
>
> ```bash
> # 1. 写入软件仓库配置
> #    注意 $basearch 要**原样保留**，dnf 会自动把它替换成 x86_64 / aarch64
> cat > /etc/yum.repos.d/docker-ce.repo <<\EOF
> [docker-ce-stable]
> name=Docker CE Stable - $basearch
> baseurl=https://mirrors.aliyun.com/docker-ce/linux/centos/10/$basearch/stable
> enabled=1
> gpgcheck=1
> gpgkey=https://mirrors.aliyun.com/docker-ce/linux/centos/gpg
> EOF
>
> # 2. 安装。注意没有 `docker-compose` 这个包 —— compose 现在是 docker 的插件
> dnf -y install docker-ce docker-ce-cli containerd.io \
>                docker-buildx-plugin docker-compose-plugin
> ```
>
> 两个容易出错的地方：
>
> - **路径里的 `centos/10`** 对应系统大版本：Rocky 10 / RHEL 10 用 `10`，
>   Rocky 9 / CentOS 9 用 `9`。写成不存在的版本就是 404。
> - **`<<\EOF` 里的反斜杠别漏**：它让 `$basearch` 不被 shell 展开，原样写进文件。
>   漏了会写成空的，仓库地址就错了。
>
> 动手前先确认这个版本的文件确实存在，能省一轮失败：
>
> ```bash
> curl -s -o /dev/null -w '%{http_code}\n' \
>   https://mirrors.aliyun.com/docker-ce/linux/centos/10/x86_64/stable/Packages/
> ```
>
> 返回 `200` 才继续。返回 `404` 说明版本号写错了，去
> `https://mirrors.aliyun.com/docker-ce/linux/centos/` 看一眼有哪些目录。

### 4.2 让 Docker 开机自启，并验证安装

```bash
# 让 docker 服务现在就启动，并且以后每次开机都自动启动
systemctl enable --now docker

# 验证
docker --version && docker compose version
```

> ### 💡 名词小课堂：systemctl
>
> Linux 上管理"后台服务"的命令。常用三个动作：
>
> | 命令 | 作用 |
> | --- | --- |
> | `systemctl start docker` | 现在启动 |
> | `systemctl enable docker` | 设为开机自启 |
> | `systemctl status docker` | 看它现在是什么状态 |
>
> `enable --now` 就是**把上面两个合起来**：既设为开机自启，又立刻启动。

**期望输出**（版本号不必和这里一致，能打印出来就行）：

```
Docker version 29.8.1, build 4a63305
Docker Compose version v5.5.1
```

> ### ⚠️ 别再以为 compose 一定是 `v2.x`
>
> 2026-09-20 实测装到的是 **Docker CE 29.8.1 + Compose v5.5.1** —— compose 插件的
> 版本号已经跳到 5.x 了。只要 `docker compose version` 能输出版本号，
> 并且**带空格的 `docker compose` 这个写法可用**，就没问题。
>
> 老教程里的 `docker-compose`（中间是连字符）是 Python 时代的独立程序，本项目不用它；
> 如果只有后者能用，说明装的是旧版，按本节重装。

### 4.3 先测一下：你的主机需不需要镜像加速

**别因为"我在国内"就直接配加速器** —— 不同机房的网络差别很大，而且同一个域名
**多次请求的结果都可能不一样**。先实测（同一条命令跑三次）：

```bash
for i in 1 2 3; do
  curl -s -m 10 -o /dev/null -w "第 $i 次: HTTP %{http_code}  耗时 %{time_total}s\n" \
    https://registry-1.docker.io/v2/
done
```

> ### 💡 名词小课堂：这段输出怎么读
>
> - `%{http_code}` 是 HTTP 状态码，`%{time_total}` 是这次请求一共花了多少秒。
> - **`401` 是正常的，代表链路是通的**。Docker Hub 要求先鉴权，不带令牌访问 `/v2/`
>   本来就该返回 401 —— 它不是错误。
> - **`000` 才是真的不通**（连接被拒绝、被重置或超时）。
>
> ⚠️ **一定要跑三次**。只测一次得出的结论不可靠：本机实测中 `download.docker.com`
> 出现过「200 → 000 → 200」的抖动，单看某一次会得到完全相反的结论。

判据很简单：

| 三次结果 | 结论 |
| --- | --- |
| 都是 401 | **不用配加速器**，跳过 4.4 |
| 出现 000 | **必须配**，做 4.4 |

### 4.4 配置镜像加速（附实测可用的公共地址）

```bash
mkdir -p /etc/docker
```

`mkdir` 是"创建目录"，`-p` 的意思是"如果父目录不存在就一起创建，如果已存在也不报错"。

```bash
cat > /etc/docker/daemon.json <<'EOF'
{
  "registry-mirrors": [
    "https://docker.1ms.run",
    "https://docker.1panel.live",
    "https://docker.m.daocloud.io"
  ],
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" },
  "live-restore": true
}
EOF
```

> ### 💡 这四项分别是什么
>
> | 配置项 | 作用 |
> | --- | --- |
> | `registry-mirrors` | 拉镜像时用的加速地址，**按顺序尝试**。放三个不同厂商的，是为了某个挂掉时还有备选 |
> | `log-driver` + `log-opts` | 限制容器日志文件的大小。**默认完全不限制**，一个疯狂打印日志的容器足以把整块磁盘撑满 |
> | `live-restore` | 重启 Docker 本身时，已运行的容器不被一起杀掉（升级 Docker、改配置后特别有用） |
>
> ### ⚠️ 上面这三个地址是实测挑出来的，别随手换
>
> 2026-09-20 在真实主机上逐个测过（判据就是 4.3 讲的 `/v2/` 响应码）：
>
> | 地址 | 结果 |
> | --- | --- |
> | `docker.1ms.run` | ✅ 401，可用 |
> | `docker.1panel.live` | ✅ 200，可用 |
> | `docker.m.daocloud.io` | ✅ 401，可用 |
> | `hub.rat.dev` | 302，可用（备选） |
> | `docker.xuanyuan.me` | 401，可用（备选） |
> | `dockerproxy.cn` | ✗ 000，不可用 |
> | `mirror.ccs.tencentyun.com` | ✗ 000（只在腾讯云自己的机房内可用） |
>
> ⚠️ **这类公共加速器是第三方服务，随时可能失效**。如果某天拉镜像突然卡住不动，
> 回到 4.3 的测法重新挑一个填进来即可。
>
> 💡 **有阿里云账号的话，用自己账号的专属加速地址更稳**：登录阿里云控制台 →
> 容器镜像服务 → 镜像加速器，会给你一段带专属 ID 的地址，
> 把上面 `registry-mirrors` 数组换成它一个就行。**注意别把中文占位符原样敲进去**
> ——那会变成非法 JSON，Docker 直接起不来。
>
> 💡 **主机在内网、或公司有内部镜像仓库**时，这里应该填内部地址，具体问一下管服务器的人。

> ### 💡 名词小课堂：这个奇怪的 `cat > 文件 <<'EOF' ... EOF` 是什么
>
> 这叫 **heredoc**（"这里有一份文档"），专门用来**把多行内容写进文件**：
>
> - `cat > /etc/docker/daemon.json`：把后面读到的东西**写进**这个文件
> - `<<'EOF'`：内容从下面开始，直到再次遇到单独一行的 `EOF` 为止
> - `'EOF'` 外面加引号，表示内容里的 `$` 之类**不做变量替换**，原样写入（更安全）
>
> 所以这整段的作用就是：把那段 JSON 写进 Docker 的配置文件。
> 这个写法在配置服务器时非常常用，值得记住。
>
> 也可以直接 `vi /etc/docker/daemon.json` 手动编辑——如果你熟悉 vi 的话。
> （新手如果误入了 vi 出不来：按 `Esc`，输入 `:q!` 回车，就能不保存退出。）

改完要重启 Docker 让它读取新配置，并确认真的生效了：

```bash
systemctl restart docker
docker info | grep -A4 "Registry Mirrors"      # 应能看到上面那三个地址
```

> 海外主机**不需要**这一步，直连官方源更快。

### 5.1 创建 `.env` 文件

Docker 部署不使用本机那份 `.env`（第三节同步时已经排除了），要在主机上**新建一个**。
仓库里带了模板 `.env.example`，复制一份即可：

```bash
cd /opt/blog/server
cp .env.example .env
```

> ### 💡 名词小课堂：`cp`
>
> copy 的缩写，`cp 源文件 目标文件`。所以这句是"把 `.env.example` 复制成 `.env`"。
> 模板文件留着不动，你的真实配置写在 `.env` 里，两者分开，互不影响。

编辑它：

```bash
vi .env
```

或者用更友好的编辑器（如果主机上有）：

```bash
nano .env
```

> ### 💡 名词小课堂：怎么在命令行里编辑文件
>
> **`nano`**（推荐新手）：
> 直接用方向键移动光标编辑，改完按 `Ctrl+O` 然后回车保存，`Ctrl+X` 退出。
> 屏幕底部会一直显示这些快捷键提示。
>
> **`vi` / `vim`**（几乎所有 Linux 都有，但操作方式反直觉）：
> 它分"模式"，打开时是**命令模式**，此时打字不会插入字符，而是当作命令。
>
> | 操作 | 按键 |
> | --- | --- |
> | 开始编辑 | 按 `i`（进入 insert 模式） |
> | 结束编辑 | 按 `Esc` |
> | 保存并退出 | `Esc` 后输入 `:wq` 回车 |
> | 不保存退出 | `Esc` 后输入 `:q!` 回车 |

### 5.2 必须修改的配置项

打开 `.env` 后，**这几项必须改**（其余可以保持原样）：

```bash
# ① 站点对外地址 —— 全篇最重要的一项
#    换成你自己的域名或 IP，**不要带末尾斜杠**
SITE_URL="https://blog.example.com"

# ② 两个密钥 —— 必须不同、必须真随机
#    ⚠️ 下面这两行**不要照抄**，要用 5.3 节的命令现场生成再粘进来
#       （生成的值长这样：4f3a9c...，共 64 个十六进制字符）
JWT_ACCESS_SECRET="粘贴 5.3 节生成的第一串"
JWT_REFRESH_SECRET="粘贴 5.3 节生成的第二串"

# ③ 数据库密码 —— 模板里默认是 blog_password，必须换掉
#    生成方式：openssl rand -hex 12
POSTGRES_PASSWORD="粘贴上一步生成的随机串"

# ④ 管理员账号 —— 首次初始化会用它创建管理员
#    自己定一个 8-64 位、同时含字母和数字的密码（别用示例里的）
ADMIN_PASSWORD="自己定的强密码"
ADMIN_EMAIL="you@example.com"

# ⑤ 明确声明这是生产环境
NODE_ENV=production
```

> **上面引号里的中文是"该填什么"的说明，不是可以直接用的值。**
> 尤其 ② ③ 两项：**必须真的换成随机串**。
> 另外注意本文档**全程不用尖括号 `<>` 做占位符** —— 原因见 3.1 节末尾的警告。

### 5.3 怎么生成密钥

不要自己想一串（人想出来的都不够随机）。用系统自带的随机数生成器：

```bash
# 两个 JWT 密钥：各生成一次，两条命令的输出必须不同
echo "JWT_ACCESS_SECRET=\"$(openssl rand -hex 32)\""
echo "JWT_REFRESH_SECRET=\"$(openssl rand -hex 32)\""

# 数据库密码：24 个十六进制字符（够强，也不会长到记不住）
echo "POSTGRES_PASSWORD=\"$(openssl rand -hex 12)\""
```

**每执行一条就把它输出的一整行复制进 `.env`。** 管理员密码（④）不用随机生成——
你需要自己记得住、能打出来，所以自己定一个 8-64 位、含字母和数字的即可。

> ### 💡 名词小课堂：`$(...)` 是什么
>
> 这叫"命令替换"：把括号里命令的**输出结果**，直接填到这个位置。
> 所以上面那句的执行顺序是：
>
> 1. 先跑 `openssl rand -hex 32`，得到一串 64 个字符的十六进制随机数（如 `a3f9...`）
> 2. 再把结果拼进 `echo` 的内容里，打印出 `JWT_ACCESS_SECRET="a3f9..."`
> 3. 你把它整行复制到 `.env` 里
>
> **关于 `openssl rand -hex 32`**：这是让 OpenSSL 生成 32 字节的真随机数据，
> 用十六进制表示出来（每字节 2 个字符，所以是 64 个字符）。
> 这个随机性来自操作系统的熵池，远比人脑想出来的"看似随机"的字符串安全。
>
> **为什么两个密钥必须不同？** 因为它们的用途不同：
> Access 令牌用于日常访问（有效期短，15 分钟），Refresh 令牌用于换取新令牌（有效期长，7 天）。
> 如果两个密钥相同，那么"access 密钥泄露"就等于"refresh 密钥也泄露"——
> 攻击者可以用它伪造长期有效的令牌。分开设置后，两者的风险是隔离的。

### 5.4 两个容易搞错的地方

**① `.env` 里的 `DATABASE_URL` 不用改。**

你会看到它写的是 `@localhost:5432/blog`。**这是故意的**，不是错误：

- **本地开发**（不用 Docker，直接 `npm run start:dev`）：用这份配置，连本机的数据库
- **Docker 部署**：`docker-compose.yml` 里的 `environment` 会用容器网络地址
  `postgres:5432` **覆盖**它

这样同一个 `.env` 文件在两种场景下都能用，不用维护两份。

**② 关于 npm 镜像源。**

`server/.npmrc` 与 `client/.npmrc` 里都写了 `registry=https://registry.npmmirror.com`（国内镜像）。

| 主机位置 | 怎么做 |
| --- | --- |
| **国内**（阿里云、腾讯云等） | 保持不动，这样构建时下载依赖快得多 |
| **海外**（Vultr、DigitalOcean 等） | 建议把这两个 `.npmrc` 里的 `registry` 行**注释掉或删掉**，改用官方源。否则反而绕远路 |

> 这条是**实测经验**：npmmirror 在国内很快，但从海外访问它可能比访问官方源还慢。

## 六、构建并启动

### 6.1 构建并启动（小内存主机务必串行）

**先构建容器镜像。** 这里有个坑：compose 默认会**并行构建** api 和 client 两个镜像，
而 `nuxt build` 是全流程里最吃内存的一步。在一台 2 核 1.7GB 的主机上，两个构建同时跑
几乎必定被系统 OOM 杀掉 —— 表现是构建中途莫名出现 `Killed` 或 `exit code 137`，
日志里看不出任何线索。所以**分开串行构建**：

```bash
cd /opt/blog/server
docker compose build api        # 先后端
docker compose build client     # 再前端
```

**再启动全部服务：**

```bash
docker compose up -d
```

| 部分 | 含义 |
| --- | --- |
| `docker compose` | 使用 compose 插件（**带空格**的写法） |
| `build api` | 只构建 `api` 这一个镜像，不碰其他服务 |
| `up` | 创建并启动 compose 文件里定义的所有服务 |
| `-d` | detached，**在后台运行**。不加这个，容器日志会一直刷满你的终端，`Ctrl+C` 一按服务就停了 |

> 老写法 `docker compose up -d --build`（构建 + 启动一步到位）在**内存充足**的主机上没问题，
> 但它在 2 核小主机上有 OOM 风险。想一步到位又不想并行的话：
>
> ```bash
> COMPOSE_PARALLEL_LIMIT=1 docker compose up -d --build
> ```

> ### ⚠️ 内存不够的两级预案
>
> **第一级：加 swap**（最有效，也最便宜）。1.7GB 内存的主机建议加 **4G swap**：
>
> ```bash
> fallocate -l 4G /swapfile
> chmod 600 /swapfile
> mkswap /swapfile
> swapon /swapfile
> echo '/swapfile none swap sw 0 0' >> /etc/fstab     # 让重启后也生效
> free -m                                              # 确认 Swap 那一行有值
> ```
>
> 磁盘代价 4G，性能代价接近于零（只在内存吃紧时才用得上）。
> 本机实测：加了 4G swap 后构建全程**没有触发过 OOM**，swap 峰值只用了约 72MB。
>
> **第二级**：还是不够，就换一台内存 ≥ 4G 的主机。

> ### 💡 名词小课堂：`up -d` 到底做了什么
>
> compose 会按顺序做这些事（docker-compose.yml 里已经声明好了顺序）：
>
> 1. **准备镜像**：api / client 用上面刚构建好的本地镜像（`blog-api:local`、
>    `blog-client:local`），`postgres` 和 `nginx` 则去下载官方现成镜像
> 2. **创建网络**：给这四个容器建一个内部网络，让它们能用**服务名**互相访问
> 3. **按依赖顺序启动**：
>    `postgres` 启动 → 等它**健康**（`healthcheck` 通过）→
>    `api` 启动 → 等它健康 → `client` 启动 → 等它健康 → `nginx` 最后启动
> 4. **建立卷**：创建 `pgdata`（存数据库）和 `uploads`（存图片）两个持久化存储
>
> **为什么要等"健康"而不是"已启动"？**
> `postgres` 容器进程起来后，还要花几秒才能真正接受连接；
> `api` 起来后也要几秒才能响应请求。如果不管这些直接启动下一层，
> 前几秒的请求就会失败（前端首屏会直接渲染报错）。
> 这就是 `depends_on` 里写 `condition: service_healthy` 的意义——
> **等真正能用了再往下走**，而不是"进程存在就算数"。

### 6.2 首次构建要多久

装依赖 + 编译前后端，视主机性能差别很大。**2 核 / 1.7GB 虚拟机上的实测值**供你估算：

| 镜像 | 主要步骤 | 实测耗时 |
| --- | --- | --- |
| `blog-api` | `npm ci`（含从 `binaries.prisma.sh` 下 Prisma 引擎）+ `nest build` + 再装一遍生产依赖 | **9 分钟** |
| `blog-client` | `npm ci` + `nuxt build` | **2 分 9 秒** |

> **改代码后重新构建会快得多**：依赖没变时 `npm ci` 那一层直接命中缓存，几秒到半分钟就完事。
> 但如果改的是 `package.json` 或 `Dockerfile`，缓存会失效，就要再等一次完整构建。

这段时间终端会输出大量日志，属正常。

期间可以开另一个终端窗口（再 `ssh` 登录一次）看进度：

```bash
cd /opt/blog/server
docker compose logs -f --tail=50
```

> `-f` 是 follow，持续输出新日志（`Ctrl+C` 只是停止查看，**不会停止容器**）。
> `--tail=50` 表示先显示最后 50 行，不要从最早开始刷屏。

### 6.3 检查启动结果

```bash
docker compose ps
```

期望看到 4 个服务：

```
NAME             IMAGE                  STATUS
blog-postgres    postgres:18-alpine     Up 2 minutes (healthy)
blog-api         blog-api:local         Up 1 minute (healthy)
blog-client      blog-client:local      Up 1 minute (healthy)
blog-nginx       nginx:1.27-alpine      Up 30 seconds
```

> 镜像名是 `blog-api:local` / `blog-client:local`，因为 `docker-compose.yml` 里给这两个服务
> 显式写了 `image:`。**不写的话** compose 会按目录名自动派生出 `server-api`、`server-client`
> 这种名字 —— 换个目录名或换台机器名字就变了，回滚旧版本、`docker save` 导出镜像时不好指名道姓。

> ### 💡 名词小课堂：`docker compose ps` 与 `docker ps` 的区别
>
> - **`docker ps`**：列出**这台机器上所有的**容器
> - **`docker compose ps`**：只列出**当前这个 compose 项目**（即当前目录的 `docker-compose.yml` 定义的）的容器
>
> 在服务器上可能有多个项目，用 `docker compose ps` 更聚焦。
> （顺便：`docker compose ps -a` 连已停止的容器也列出来。）

**关于状态为 `starting`**：

`api` 和 `client` 的 healthcheck 都设了 `start_period`（启动宽限期，20～30 秒）。
在这段时间内，状态会显示 `starting` 而**不是** `healthy`——**这是正常的**，
等一下再 `docker compose ps` 就会变绿。

`nginx` **没有** healthcheck（它只是个转发器，没什么可检的），
所以它的 STATUS 栏不会显示 `(healthy)`，这也正常。

### 6.4 如果 `api` 起不来

先看日志：

```bash
docker compose logs --tail=80 api
```

**最可能的原因：`SITE_URL` 没设置。** 这种情况下 compose 会直接拒绝启动，
错误信息里会有 `请在 server/.env 里设置站点对外地址`。

> 为什么报错信息是中文？因为 `docker-compose.yml` 里写的是
> `${SITE_URL:?请在 server/.env 里设置站点对外地址}`。
> 这个语法的含义是：
>
> | 写法 | 含义 |
> | --- | --- |
> | `${SITE_URL}` | 取 `SITE_URL` 的值；没设置的话就是**空**，不报错 |
> | `${SITE_URL:-默认值}` | 取 `SITE_URL` 的值；没设置就用**默认值** |
> | `${SITE_URL:?错误提示}` | 取 `SITE_URL` 的值；**没设置就直接报错退出**，并显示这句提示 |
>
> 项目里用的是第三种。这是刻意的设计——就是第一节第 3 件事说的那个原因：
> 宁可启动失败，也不要悄悄生成一份指向 `localhost` 的 sitemap。

（会尝试重复插入管理员账号）。

### 7.2 等数据库健康后执行

先确认 `postgres` 已经是 `healthy`：

```bash
docker compose ps postgres
```

看到 `(healthy)` 后，执行：

```bash
cd /opt/blog/server

# ① 建表：把本机的 db/schema.sql 通过管道喂给容器里的 psql 执行
docker compose exec -T postgres psql -U blog -d blog < ../db/schema.sql

# ② 初始化管理员与基础分类
docker compose exec api node dist/seed.js
```

**这两条命令逐段拆解**：

先看第 ① 条 `docker compose exec -T postgres psql -U blog -d blog < ../db/schema.sql`：

| 部分 | 含义 |
| --- | --- |
| `docker compose exec` | 在**正在运行的容器里**执行一条命令（这个容器会消失，不像 `run`） |
| `-T` | 不分配伪终端（no TTY）。**从文件重定向输入时必须加**，否则 psql 会以为自己在跟人交互而行为异常 |
| `postgres` | 在哪个容器里执行 —— 服务名叫 `postgres` 的那个 |
| `psql -U blog -d blog` | 要执行的命令：用 `blog` 用户（`-U`），连 `blog` 数据库（`-d`） |
| `< ../db/schema.sql` | **输入重定向**：把本机这个文件的内容，当作 psql 的标准输入喂给它 |

> ### 💡 名词小课堂：`<` 和 `>` 是什么
>
> 这两个符号叫**重定向**，来自 Unix 的古老设计：
>
> | 符号 | 含义 | 例子 |
> | --- | --- | --- |
> | `<` | 把文件内容送进程序，当作它的**输入** | `psql < schema.sql` = 让 psql 执行这个文件里的 SQL |
> | `>` | 把程序的**输出**写进文件（会覆盖原有内容） | `docker compose logs > log.txt` |
> | `>>` | 同上，但是**追加**到文件末尾，不覆盖 | （备份命令里用到过） |
> | `\|` | 把左边命令的输出，接给右边命令当输入 | `curl ... \| sh` |
>
> 注意 `<` 在这里有个微妙之处：`docker compose exec` 的输入会**转发到容器内部**，
> 所以 `psql` 从"标准输入"读到的就是文件内容，等于在 psql 里粘贴了一整套 SQL。

再看第 ② 条 `docker compose exec api node dist/seed.js`：

- 在 `api` 容器里执行 `node dist/seed.js`
- `dist/seed.js` 是 `npm run build` 时由 TypeScript 编译出来的产物

> **为什么生产环境能直接跑 `.js` 而不是 `.ts`？**
> 因为 `dist/` 里已经是编译好的 JavaScript。而且它是**构建镜像时就生成好的**——
> 你可以自己进容器看一眼：
>
> ```bash
> docker compose exec api ls dist/ | head
> ```
>
> 这也是为什么生产环境不需要 `ts-node`（一个"直接运行 TypeScript"的工具）：
> 编译发生在构建阶段，运行阶段只跑成品。

## 八、验收：确认"真的能用"

### 8.1 逐层检查

从最内层开始往外查，哪一层出问题就查哪一层，这样定位最快。

**① 后端自己活着吗**（在主机上执行，直连 api 容器的端口）

```bash
curl -s http://127.0.0.1:3000/health
```

> ### 💡 名词小课堂：curl
>
> 一个"用命令行的方式发 HTTP 请求"的工具，相当于**没有界面的浏览器**。
>
> | 选项 | 含义 |
> | --- | --- |
> | `-s` | silent，不显示进度条（但保留响应内容） |
> | `-I` | 只显示响应头，不显示正文（相当于 HEAD 请求） |
> | `-o 文件` | 把响应保存到文件而不是打印到屏幕 |
>
> 所以 `curl -s http://...` 的意思是"发个 GET 请求，把返回的内容打印出来"。
> 排查网络问题时**它是你最常用的工具**。

期望输出里含 `"database":"up"`（说明后端不仅活着，还连上了数据库）。

**② 前端 SSR 能渲染吗**（同样在主机上）

```bash
# -I 只看响应头，head -3 取前 3 行
curl -sI http://127.0.0.1/ | head -3

# 看页面标题对不对
curl -s http://127.0.0.1/ | grep -o '<title>[^<]*</title>'
```

第一条应返回 `HTTP/1.1 200 OK`；第二条应输出你的站点标题。

> ### 💡 名词小课堂：grep -o
>
> `grep` 是"从文本里找符合条件的行"。
> `-o`（only-matching）表示"**只打印匹配到的那部分**"，而不是整行。
>
> 因为 HTML 是一大坨，`grep -o '<title>[^<]*</title>'` 就只把标题标签摘出来，
> 看起来干净得多。
>
> 这里的 `[^<]*` 是正则表达式，读作"任意多个**不是 `<`** 的字符"——
> 也就是"标题文字本身"。

**③ 站点地图和订阅文件**（由后端提供，nginx 转发的）

```bash
curl -s http://127.0.0.1/sitemap.xml | head -5
curl -s http://127.0.0.1/rss.xml | head -5
```

**④ 从公网访问**（把 IP 换成你的）

```bash
curl -sI http://123.45.67.89/ | head -3
```

如果①②③都通、④不通，问题在**安全组没放行 80 端口**（回到第二节检查）。
如果①通、②不通，问题在 nginx 转发或前端容器。

### 8.2 ⭐ 关键一步：确认 sitemap 里是真实地址

这一步**专门用来抓"地址配错"**这类问题，是整份文档里最有价值的一条检查。

```bash
curl -s http://127.0.0.1/sitemap.xml | grep -o '<loc>[^<]*</loc>' | head
```

**期望看到**：

```xml
<loc>https://blog.example.com/</loc>
<loc>https://blog.example.com/articles/欢迎来到这个博客</loc>
<loc>https://blog.example.com/categories/backend</loc>
...
```

**如果看到 `localhost`，说明 `SITE_URL` 没生效**。

> **为什么偏偏是这一条最容易出错？**
> 因为改 `SITE_URL` 后，光 `docker compose restart` 是**不够的**——
> 环境变量是容器**创建时**注入的，`restart` 只是重启进程，不会重新读配置。
> 必须**重新创建容器**：
>
> ```bash
> docker compose up -d --force-recreate api client
> ```
>
> | 命令 | 效果 |
> | --- | --- |
> | `docker compose restart api` | 重启容器里的进程，**环境变量不变** |
> | `docker compose up -d api` | 如果配置没变，什么都不做 |
> | `docker compose up -d --force-recreate api` | **强制删掉旧容器、用新配置重建**，环境变量生效 |
>
> 这个区别很微妙，但正是"改完配置怎么不生效"这类问题的常见原因。

### 8.3 再跑一次「订阅源链接连通性」检查

仓库里带了一个自动化检查脚本 `server/scripts/check-feed-links.mjs`。
它做的事很实在：**把 sitemap 里的每条链接、RSS 里的每篇文章链接，真的请求一遍，要求全部返回 200**。

> **为什么需要这么个脚本？**
> 因为本项目曾经踩过一个坑：后端生成 sitemap 时把路径写成了 `/article/xxx`（单数），
> 而前端的真实路由是 `/articles/xxx`（**复数**）。
> 结果是 sitemap 里除首页外**每一条链接都是 404**，而整条链路**不报任何错**——
> 站点看起来完全正常，只是搜索引擎收录不到任何文章。
> 这类"静默失效"只能靠"真的去请求一遍"来发现。

它不依赖任何 npm 包，容器里的 Node 直接能跑：

```bash
cd /opt/blog/server

# 方式一：在容器内跑（验证 api + client 两个容器之间的链路）
docker compose exec -e BACKEND=http://api:3000 -e FRONT=http://client:3001 \
  api node scripts/check-feed-links.mjs

# 方式二：验证「经过 nginx」的完整链路（需要主机上装了 Node 18+）
BACKEND=http://127.0.0.1 FRONT=http://127.0.0.1 node scripts/check-feed-links.mjs
```

**期望输出**（全部 200 才算过）：

```
sitemap.xml: HTTP 200，共 9 条 URL
  ✓ 200  /
  ✓ 200  /archives
  ✓ 200  /articles/欢迎来到这个博客
  ✓ 200  /categories/backend
  ✓ 200  /categories/frontend
  ✓ 200  /categories/devops
  ✓ 200  /categories/essay
  ✓ 200  /tags/公告
  ✓ 200  /author/admin

rss.xml: HTTP 200，文章链接 1 条
  ✓ 200  /articles/欢迎来到这个博客

✅ 全部 10 条链接均可用
```

> ⚠️ **如果报 `Cannot find module '/app/scripts/check-feed-links.mjs'`**：
> 说明你的镜像是 2026-09-20 之前构建的 —— 那时 `server/Dockerfile` 的 runner 阶段
> 只拷贝了 `dist`，脚本根本没进镜像，而文档却让你去容器里跑它。现已修复，重新
> `docker compose build api` 即可。
>
> ⚠️ **中文 slug 的编码坑，手查时必看**：文章的 slug 是中文时，sitemap 里会写成
> `/articles/%E6%AC%A2%E8%BF%8E%E6%9D%A5%E5%88%B0...`（百分号编码）。
> 所以 **`grep '欢迎来到' sitemap.xml` 是搜不到的**，会让你误判成"没收录"。
> 正确做法是搜路径段：`grep -c '/articles/'`。
> 上面这个脚本会先 `decodeURIComponent` 再显示，所以它打印出来是能读的中文路径。

> ### 💡 名词小课堂：`-e` 与环境变量
>
> `docker compose exec -e BACKEND=http://api:3000 ...` 中的 `-e` 是 environment，
> 意思是"**在这条命令的环境里，额外加上这个变量**"。
> 它只影响这一次执行，不会改动容器本身的配置。
>
> 这两个变量的作用：脚本会把 sitemap 里的对外地址（如 `https://blog.example.com`）
> **替换成探测地址**（`http://api:3000`），所以它校验的是**路径对不对**，
> 而不是域名通不通。

> ⚠️ **这个脚本查不出「SITE_URL 配错」**——那是 8.2 节那条 `grep <loc>` 的职责。
> 两者的分工别搞混了：
>
> | 检查 | 能发现的问题 |
> | --- | --- |
> | `grep '<loc>'` | 域名配错（如指向 localhost） |
> | `check-feed-links.mjs` | 路径写错（如 `/article/` vs `/articles/`） |

## 九、配置 HTTPS（有域名必做）

### 9.1 为什么必须配

不配 HTTPS 的话，**用户登录时输入的用户名和密码是明文经过公网的**。
链路上的任何一个节点（公共 WiFi 的路由器、运营商、中间的网络设备）都能直接读到。
**这不能上线。**

配了之后，浏览器和服务器之间的所有内容都被加密，中途截获也读不懂。

> ### 💡 名词小课堂：HTTPS 是怎么工作的（简化版）
>
> 1. 你的服务器**持有两样东西**：一张**证书**（公开的，包含你的域名和公钥）
>    和一个**私钥**（保密的，只有服务器有）
> 2. 浏览器访问时，服务器先把证书给它
> 3. 浏览器验证：这张证书是不是权威机构签发的？里面的域名跟我访问的一致吗？
>    （这就是为什么证书要"申请"——需要第三方背书）
> 4. 验证通过后，双方用证书/私钥协商出一把**临时会话密钥**，之后的通信都用它加密
> 5. **私钥绝不能泄露**——泄露了，别人就能冒充你的网站
>
> **Let's Encrypt** 是一家免费签发证书的机构（公益组织），
> **certbot** 是它的官方客户端，能自动完成"申请 → 验证域名归属 → 下载证书"这一整套流程。
> 证书有效期 90 天，所以需要定期续期（第 9.4 节有定时任务）。

### 9.2 第一步：申请证书

certbot 需要验证"这个域名真的是你在控制"。最简单的方式是 **standalone 模式**：
临时占住 80 端口做验证。

```bash
# 先建好存证书和临时文件的目录
mkdir -p /opt/blog/server/certs /opt/blog/certbot-www
```

申请时需要**短暂停掉 nginx**（因为要让 certbot 独占 80 端口）：

```bash
cd /opt/blog/server

# 停掉 nginx 容器
docker compose stop nginx

# 用 certbot 的官方镜像申请证书
docker run --rm -p 80:80 \
  -v /opt/blog/server/certs:/etc/letsencrypt \
  certbot/certbot certonly --standalone \
  -d blog.example.com --agree-tos -m you@example.com --no-eff-email

# 申请完再把 nginx 拉起来
docker compose start nginx
```

逐项说明：

| 部分 | 含义 |
| --- | --- |
| `docker run --rm` | 启动一个一次性容器，**用完自动删除**（`--rm`）。certbot 只是个工具，不需要常驻 |
| `-p 80:80` | 把主机的 80 端口给它，这样它才能响应 Let's Encrypt 的验证请求 |
| `-v /opt/blog/server/certs:/etc/letsencrypt` | 把主机目录挂进容器。**证书要存到主机上**，否则容器一删证书就没了 |
| `certonly` | 只申请证书，不自动改 Nginx 配置 |
| `--standalone` | 自己起一个临时小服务器来响应验证，不依赖 Nginx |
| `-d blog.example.com` | 要申请的域名（换成你自己的） |
| `--agree-tos` | 同意服务条款（不想交互式确认） |
| `-m you@example.com` | 你的邮箱，证书快过期时会提醒 |
| `--no-eff-email` | 不要把邮箱分享给 EFF 基金会（可选，不影响功能） |

成功后，证书会出现在 `/opt/blog/server/certs/live/blog.example.com/` 目录下，
里面最关键的两个文件是：

| 文件 | 用途 |
| --- | --- |
| `fullchain.pem` | 证书链（公开，可以给别人看） |
| `privkey.pem` | **私钥**（绝不能外泄） |

> ⚠️ **前提**：`blog.example.com` 的 DNS 必须已经解析到你这台主机的 IP。
> 否则 Let's Encrypt 找不到你的服务器，验证会失败。
> 在云服务商的域名控制台加一条 A 记录即可（记录值填你的公网 IP）。

### 9.3 第二步：让 nginx 用上证书

**① 打开编排里的两行注释**（`server/docker-compose.yml` 的 `nginx` 服务部分）：

```yaml
    ports:
      - '80:80'
      - '443:443'                       # ← 去掉注释
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - uploads:/var/www/uploads:ro
      - ./certs:/etc/nginx/certs:ro     # ← 去掉注释
```

> 注意挂载路径的区别：主机上是 `./certs`，容器里是 `/etc/nginx/certs`。
> 所以下一步写 Nginx 配置时，路径要用**容器内的那一个**。

**② 修改 `server/nginx.conf`：把原来的 80 段改成"跳转到 HTTPS"，再新增一个 443 段。**

原来的样子（第 29 行开始）：

```nginx
server {
    listen 80;
    server_name _;
    # ...下面一堆 location...
}
```

改成：

```nginx
# ---- 80 端口：只负责跳转到 HTTPS ----
server {
    listen 80;
    server_name blog.example.com;

    # 证书续期时的验证路径要放行，否则续期会失败
    location /.well-known/acme-challenge/ { root /var/www/certbot; }

    # 其他所有请求：永久重定向到 HTTPS
    location / { return 301 https://$host$request_uri; }
}

# ---- 443 端口：真正干活的 ----
server {
    listen 443 ssl;
    http2 on;
    server_name blog.example.com;

    # 证书路径（注意是容器内的路径）
    ssl_certificate     /etc/nginx/certs/live/blog.example.com/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/live/blog.example.com/privkey.pem;

    # 只允许较新的 TLS 版本，老版本有已知漏洞
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;

    # ↓↓↓ 把原来 80 段里的这些配置整段搬过来，一字不改 ↓↓↓
    #   client_max_body_size 10m;
    #   server_tokens off;
    #   gzip 相关四行
    #   location ^~ /uploads/          （上传图片直出）
    #   location ~ ^/api/v1/auth/...   （认证接口限流）
    #   location ~ ^/api/v1/(articles/...（写操作限流）
    #   location /api/                 （后端 API）
    #   location = /health, /sitemap.xml, /rss.xml, /robots.txt
    #   location /                     （前端 SSR，必须是最后一条）
}
```

> ### ⚠️ 这一步最容易犯错的地方
>
> **两个 `server` 块里的 `location` 规则必须是同一套。**
> 新手常见错误是只改了 `listen 443` 而忘了搬 `location`，
> 结果 HTTPS 下首页能开、`/api/` 全部 404——因为 443 段里没有转发 `/api/` 的规则。
>
> 一种更稳妥的做法是把公共部分抽成一个 `include` 文件，两个 `server` 块都引用它。
> 本项目目前**故意用内联写法**：少一个文件就少一处"配置齐全了但文件没同步"的可能。
> 要不要重构成 include，你自己权衡。
>
> **另外**：`location /` 必须是**最后一条**规则——它是兜底规则，
> 前面那些 `/api/`、`/uploads/`、`/sitemap.xml` 必须先匹配到。顺序错了整个站点都会怪。

**③ `server_name _` 记得改成你的域名。**

`_` 是"匹配任何域名"的意思。配 HTTPS 时必须写真实域名，
否则 nginx 不知道用哪张证书。

### 9.4 第三步：让配置生效

```bash
cd /opt/blog/server

# 让新的端口映射与证书挂载生效
docker compose up -d

# 检查 Nginx 配置语法（重要！先检查再重载）
docker compose exec nginx nginx -t

# 语法通过后重载配置（不中断服务）
docker compose exec nginx nginx -s reload
```

> ### 💡 名词小课堂：`nginx -t` 与 `-s reload`
>
> - **`nginx -t`**（test）：只**检查配置文件的语法**，不真的加载。
>   配 Nginx 时**养成习惯：每次改完先 `-t`**。
>   如果配置文件有语法错误就直接 reload，Nginx 会拒绝加载新配置（旧配置还在跑），
>   此时你会以为"改了但没生效"，其实是配置根本没被接受。
> - **`-s reload`**（signal reload）：**优雅地重新加载配置**——
>   老的工作进程处理完手头的请求再退出，新的工作进程接管新请求。
>   所以用户完全感觉不到服务中断。这比 `docker compose restart nginx` 好得多。

**④ 别忘了把 `.env` 里的地址改成 https。**

```bash
vi .env
# 把 SITE_URL 改成 https://blog.example.com
```

然后让前后端重新读取配置：

```bash
docker compose up -d --force-recreate api client
```

> **为什么必须 `--force-recreate`？** 第 8.2 节讲过：环境变量在容器**创建**时注入，
> 改 `.env` 后不清不重建容器，新值不会生效。
> 忘了这一步的症状就是"sitemap 里还是 http 地址"。

### 9.5 第四步：设置证书自动续期

Let's Encrypt 的证书**只有 90 天有效期**。手动续期迟早会忘（忘了的后果是某天网站突然
提示"证书已过期，连接不安全"）。设个定时任务让它自动续：

```bash
# 每月 1 号凌晨 3:30 尝试续期
( crontab -l 2>/dev/null; echo '30 3 1 * * cd /opt/blog/server && docker run --rm -v /opt/blog/server/certs:/etc/letsencrypt certbot/certbot renew --webroot -w /var/www/certbot && docker compose exec nginx nginx -s reload' ) | crontab -
```

> ### 💡 名词小课堂：crontab 与定时任务
>
> `cron` 是 Linux 上的**定时任务调度器**，`crontab` 是管理任务列表的命令。
>
> 时间表达式有五个字段，从左到右：
>
> ```
> 30   3    1    *    *
> │    │    │    │    │
> │    │    │    │    └── 星期几 (0-7，0 和 7 都是周日)
> │    │    │    └─────── 月份 (1-12)
> │    │    └──────────── 日 (1-31)
> │    └───────────────── 小时 (0-23)
> └────────────────────── 分钟 (0-59)
> ```
>
> 所以 `30 3 1 * *` = **每月 1 号 3:30**。`*` 表示"每一个"。
>
> 上面那条命令的技巧是：
> `crontab -l` 列出当前已有任务（`2>/dev/null` 表示"如果还没任务，别报错"），
> 然后用 `( ... )` 把旧任务的输出 + 新任务**合并**，一次性喂回 `crontab -`。
> 这样写的好处是**不会覆盖你已有的其他定时任务**。
>
> 查看已设置的任务：
>
> ```bash
> crontab -l
> ```

## 十、日常运维

### 10.1 更新代码

流程和首次部署几乎一样，只是**不要重复做初始化**（第七节那两条命令）。

在**本机**重新传一次代码。命令和 3.4 节**完全一样**——全量传就行，
本项目每次改动通常只有几百 KB，不到一秒钟：

```bash
cd /c/Users/lx/WorkBuddy/2026-09-17-17-12-31

tar czf - \
  --exclude='node_modules' --exclude='.output' --exclude='.nuxt' \
  --exclude='dist' --exclude='.env' --exclude='.workbuddy' \
  . | ssh root@$SERVER "mkdir -p $REMOTE && tar xzf - -C $REMOTE"
```

> 💡 变量 `$SERVER` / `$REMOTE` 是 3.4 节定义的。
> **重开终端窗口后它们就没了**，先重新跑一遍那三行定义（`SERVER=...` / `LOCAL=...` / `REMOTE=...`）。
> 忘了定义会得到一个奇怪的报错：`ssh: Could not resolve hostname`。

> ⚠️ **有一个语义差异要知道：`tar` 解包只会覆盖同名文件，不会删除多余文件。**
> 也就是说，如果你**删除了**本机的某个源文件，它在服务器上会**残留**下来。
>
> 绝大多数情况这没关系——多出来的源文件只是躺在磁盘上，不会被容器打包进去。
> 但如果残留的是 `server/src/` 下的 `.ts` 文件，它**会**被 `npm run build` 编进去，
> 可能造成"我明明删了，怎么还在"的困惑。
>
> 遇到这种情况，正确做法是：先用 `ls` 在服务器上确认多出来的是哪几个文件，
> **单独删那几个**（`rm server/src/xxx.ts`），而不是对整个目录做批量清理。
> 需要时告诉我具体是哪些，我给你一条安全的命令。

先在**主机上**重建（下一节）。

然后在**主机上**重建：

```bash
cd /opt/blog/server
docker compose build api        # 先后端
docker compose build client     # 再前端
docker compose up -d
```

> ⚠️ **为什么不用 `docker compose up -d --build`**：它会**并行构建**两个镜像。
> 内存小的主机上这会触发 OOM（构建中途莫名 `Killed`），理由详见 6.1 节。
> 内存 ≥ 4G 的主机可以图省事直接用它。

compose 会自动只重建有变化的镜像，其余容器保持运行。

**只改了一边时，可以只重建一个**（更省时间）：

```bash
docker compose build api && docker compose up -d api        # 只重建后端
docker compose build client && docker compose up -d client  # 只重建前端
```

> 💡 **判断改的是哪边**：改了 `server/` 里的东西 → 重建 `api`；
> 改了 `client/` 里的东西 → 重建 `client`；
> 改了 `db/schema.sql` 或 `docker-compose.yml` → 两边都可能要重建。
>
> ⚠️ **绝对不要用 `docker compose down -v`**。
> `-v` 会删掉 `pgdata` 和 `uploads` 两个卷，也就是**数据库里所有文章 + 用户上传的所有图片**。
> 日常更新用 `up -d` 就够了，根本不需要 `down`。

### 10.3 直接查数据库

```bash
docker compose exec postgres psql -U blog -d blog
```

进入后会看到 `blog=#` 提示符，之后可以敲 SQL：

```sql
-- 看有哪些表
\dt

-- 看有哪些索引
\di

-- 看用户
select id, username, role, status from users;

-- 看已发布的文章
select id, title, status, published_at from articles where status = 'published';

-- 退出
\q
```

> ### 💡 名词小课堂：psql 的"反斜杠命令"
>
> 以 `\` 开头的是 psql 自己的内置命令，**不是 SQL**，末尾**不要加分号**：
>
> | 命令 | 作用 |
> | --- | --- |
> | `\dt` | 列出所有表（t = tables） |
> | `\di` | 列出所有索引（i = indexes） |
> | `\dv` | 列出所有视图（v = views） |
> | `\d 表名` | 看某张表的结构 |
> | `\l` | 列出所有数据库 |
> | `\q` | 退出 |
>
> 而 SQL 语句（`select ...`）**必须用分号结尾**才能执行。

### 10.4 备份

**要备份三样东西**：数据库、上传的图片、配置文件。

```bash
mkdir -p /opt/backup
cd /opt/blog/server

# ⚠️ 先确认真实的卷名（下一步要用），通常形如 server_uploads
docker volume ls

# ① 数据库：导出成一个压缩的 SQL 文件
docker compose exec -T postgres pg_dump -U blog blog | gzip > /opt/backup/db-$(date +%F).sql.gz

# ② 上传的图片：卷里的文件用一次性容器打包（因为卷在容器内部，主机上直接看不到）
#    ↓ 把 server_uploads 换成上一步查到的真实卷名
docker run --rm -v server_uploads:/data -v /opt/backup:/backup alpine \
  tar czf /backup/uploads-$(date +%F).tar.gz -C /data .

# ③ 配置（里面有密钥）
cp .env /opt/backup/env-$(date +%F).bak
```

逐项说明：

| 部分 | 含义 |
| --- | --- |
| `pg_dump -U blog blog` | 用 `blog` 用户，把 `blog` 这个库**完整导出**成 SQL 文本 |
| `\| gzip > 文件` | 导出的文本压缩后写进文件（SQL 文本压缩率很高） |
| `$(date +%F)` | 命令替换，插入今天的日期，如 `2026-09-20`。这样每天的备份不会互相覆盖 |
| `-v server_uploads:/data` | 把**图片卷**挂到容器的 `/data`（注意是 `server_uploads`，不是 `blog_uploads`） |
| `alpine` | 一个极小的 Linux 镜像，里面有 `tar` 命令 |
| `tar czf /backup/xxx.tar.gz -C /data .` | 进到 `/data` 目录，把它里面**所有东西**打包压缩 |

> **⚠️ 卷的名字必须自己确认，不能猜。**
> Docker 会给卷加一个前缀，默认是"**项目名**"（一般取 compose 文件所在目录名）。
> 本项目的 compose 文件在 `server/` 目录下，所以卷名通常是 **`server_uploads`**、
> **`server_pgdata`**，而**不是** `blog_uploads`（`blog-` 那个前缀是容器的 `container_name`，
> 和卷名不是一回事——这两个很容易搞混）。
>
> ```bash
> docker volume ls
> ```
>
> **为什么这一点特别重要**：如果你在 `docker run -v 卷名:/data` 里写了一个**不存在的卷名**，
> Docker **不会报错**，而是**默默新建一个空卷**。于是你以为备份成功了，
> 实际上备份出来的是一个空目录——**直到你需要恢复的那一天才会发现**。
> 所以：**先 `docker volume ls` 看清楚，再执行备份。**
> 备份完也顺手确认一下文件大小不为 0：
>
> ```bash
> ls -lh /opt/backup/
> ```

**恢复数据库**：

```bash
gunzip -c /opt/backup/db-2026-09-20.sql.gz \
  | docker compose exec -T postgres psql -U blog -d blog
```

> 💡 注意这里是 `gunzip -c`（解压到标准输出），而不是 `gunzip` 直接解压文件。
> `-c` 表示"结果写到屏幕"（这里被管道接走了），**不会破坏原来的 `.gz` 文件**。
> 这很重要——万一恢复失败，你还有原始备份。

> ### ⚠️ 如果是要"清空重来"（灾难恢复），直接跑上面这条会**报错**
>
> `pg_dump` 默认是**增量式**导出（只含 `CREATE TABLE`，不含 `DROP TABLE`），
> 而且**库里已有的数据不会被清掉** —— 直接往一个还有数据的库里灌，
> 轻则主键冲突报错，重则灌进去一半、库处于半损坏状态。
>
> 灾难恢复的正确姿势是**先删库再重建**，但这时会撞上第二个坑：
>
> ```bash
> # 想删库，却被 api 容器占着连接 → 失败
> docker compose exec -T postgres psql -U blog -d postgres -c "drop database blog;"
> # ERROR:  database "blog" is being accessed by other users
> # DETAIL:  There is 4 other session using the database.
> ```
>
> **实测（2026-09-20）**：api 容器默认对 `blog` 库持有 **4 条连接**
> （`DATABASE_URL` 里 `connection_limit=10`），所以这条报错**一定会发生**。
> 两种解法，任选其一：
>
> ```bash
> # 解法 A（推荐，最直观）：先把写库的服务停掉，再删库
> cd /opt/blog/server
> docker compose stop api client nginx
> docker compose exec -T postgres psql -U blog -d postgres -c "drop database blog;"
> docker compose exec -T postgres psql -U blog -d postgres -c "create database blog owner blog;"
> gunzip -c /opt/backup/db-2026-09-20.sql.gz \
>   | docker compose exec -T postgres psql -U blog -d blog -v ON_ERROR_STOP=1
> docker compose start api client nginx
>
> # 解法 B（PG13+，一条命令踢掉所有连接）
> docker compose exec -T postgres psql -U blog -d postgres \
>   -c "drop database blog with (force);"
> # 实测这条会成功返回 DROP DATABASE
> ```
>
> 恢复完记得**再跑一次第八节的验收**（尤其是 8.3 的订阅源链接检查），
> 并确认那 3 个中文搜索索引还在（见 15.3 节的检查语句）。
>
> ✅ 这条「备份 → 恢复」链路已于 **2026-09-20 完整演练通过**：
> 三条备份命令原样执行成功（dump 压缩后 7151 字节、`gzip -t` 通过、
> env 备份与线上逐字节一致），再解压灌进一个全新空库，
> 表/视图/索引/触发器/扩展/用户/文章/分类**逐项与线上完全一致**，
> 恢复日志 0 条 error；演练用的临时库已删除、线上站点仍 200。
> 完整数据见 **15.4 节**。

**建议**：把这三条命令存成一个脚本，加到 crontab 里每天自动跑。
比如每天凌晨 4 点：

```bash
( crontab -l 2>/dev/null; echo '0 4 * * * cd /opt/blog/server && docker compose exec -T postgres pg_dump -U blog blog | gzip > /opt/backup/db-$(date +\%F).sql.gz' ) | crontab -
```

> ⚠️ 注意 crontab 里的 `%` 需要转义成 `\%`（cron 对 `%` 有特殊含义），
> 所以写的是 `$(date +\%F)`。

### 10.5 开机自启

**不需要额外配置。** 因为：

1. 四个服务在 `docker-compose.yml` 里都写了 `restart: unless-stopped`——
   意思是"除非你手动停了它，否则它挂掉就自动重启"
2. 第四节的 `systemctl enable --now docker` 已经让 Docker 本身开机自启

所以主机重启后，Docker 起来 → 四个容器自动跟着起来。

> **`restart: unless-stopped` 与 `restart: always` 的区别**：
> `always` 会在"你手动 `docker compose stop` 之后又重启主机"时也把容器拉起来；
> `unless-stopped` 则尊重你的手动停止。调试时手动停了某个容器，
> 不会因为主机重启又莫名其妙跑起来——这个行为更符合直觉。

### 10.6 密码：怎么改、忘了怎么办

#### 正常改密码（走界面，推荐）

1. 从 `/login` 登录（字段是「**用户名或邮箱**」，管理员填 `admin`）
2. 登录后侧栏点「**个人资料**」（路径 `/dashboard/profile`）
3. 右侧「**修改密码**」卡片：填当前密码 → 新密码 → 再输一次 → 点「修改密码」

新密码规则（**前端和后端都校验**，前端先拦一道省一次请求）：

- 长度 **8–64 位**
- 必须**同时**包含字母和数字
- 两次输入必须一致

#### ⚠️ 改密码**不会**把别的设备踢下线（别误解，这条很重要）

界面上那句提示写着"修改后其他设备上的登录会失效，需要重新登录"——
**这句话与实际行为不符**。2026-09-20 用一次性账号实测（验证完即删）：

| 检查项 | 实测结果 |
| --- | --- |
| 改密后，用**改密前**签发的 access token 调 `/api/v1/auth/me` | **200 —— 仍然有效** |
| 改密后，用**改密前**的 refresh token 调 `/api/v1/auth/refresh` | **200 —— 还能换出一对新 token** |

原因：本项目用的是**无状态 JWT**，签名载荷里只有用户 ID / 用户名 / 角色，
**不含任何会随改密而变的凭据**；而 `/auth/refresh` 只检查账号是不是 `disabled`，
**不检查密码有没有变过**。所以旧设备不但不会立刻掉线，还能**一直续期、永不掉线**。

**你该怎么做，取决于你为什么改密码：**

- **只想换个更好记/更安全的密码** → 照上面正常改就行，完全不受影响。
- **因为怀疑密码外泄才来改的** → 请注意：改密码**不足以**把攻击者踢下线。
  真要立刻断开**所有**已登录会话，眼下只有一个办法——
  换掉 `server/.env` 里的两个 JWT 密钥再重启 api：

  ```bash
  cd /opt/blog/server
  # 编辑 .env，把 JWT_ACCESS_SECRET 与 JWT_REFRESH_SECRET 换成新的随机值
  # 生成新值：openssl rand -hex 32
  docker compose up -d --force-recreate api
  ```

  代价是**所有人（包括你自己）都要重新登录**——简单粗暴，但立即生效。

  > 更优雅的做法是让后端支持「改密即吊销旧令牌」（给 `users` 加一个令牌版本号、
  > 写进 JWT、改密时 +1、校验时比对）。本项目**尚未实现**，属已知取舍。

#### 忘了密码怎么办（`admin` 是唯一账号时必读）

线上目前**只有 `admin` 一个账号**（`select count(*) from users` = 1），
所以**没有第二个管理员能帮你重置**。另外请注意：

> **重跑 `node dist/seed.js` 不会覆盖已存在管理员的密码。**
> `src/seed.ts` 对已存在的 admin 只修正 `role` / `status`，**不动 `password_hash`**。
> 别指望用 seed 找回密码。

唯一的兜底是自己往库里写一条格式正确的哈希。存储格式是
`scrypt$N$r$p$<saltBase64>$<hashBase64>`，参数 `N=32768, r=8, p=1`。
api 容器里有 Node，可以现场生成：

```bash
cd /opt/blog/server
NEWPW='改成你的新密码'          # 必须满足 8-64 位且同时含字母与数字

HASH=$(docker compose exec -T -e PW="$NEWPW" api node -e '
const { randomBytes, scrypt } = require("crypto");
const { promisify } = require("util");
const s = promisify(scrypt);
const N = 32768, r = 8, p = 1;
const salt = randomBytes(16);
s(process.env.PW, salt, 64, { N, r, p, maxmem: 128 * N * r * 2 }).then((d) => {
  process.stdout.write(["scrypt", N, r, p, salt.toString("base64"), d.toString("base64")].join("$"));
});
' </dev/null | tr -d '\r')

docker compose exec -T postgres psql -U blog -d blog </dev/null \
  -c "update users set password_hash = '$HASH' where username = 'admin';"
```

写完后立刻用新密码登录一次确认。

> **两个坑，都实测过：**
>
> 1. **`psql -c` 不做 `:'变量'` 插值** —— 会把冒号原样发给服务端，报
>    `syntax error at or near ":"`。所以要像上面这样把哈希**直接拼进 SQL 字符串**。
>    哈希只含 `A-Za-z0-9+/=$`，不含引号，拼进去是安全的。
> 2. **手写别的算法哈希没用**：`PasswordService.verify` 见到不以 `scrypt$` 开头的值
>    **一律判定失败**（这是刻意的——绝不做"格式不对就放行"这种兜底），
>    所以必须用上面这个格式。

> ✅ 这条流程已于 **2026-09-20 在主机上实测通过**：写入哈希 → 用该明文密码登录返回
> **200** → 错误密码返回 **401** → 验证完删除一次性账号，`admin` 不受影响。

## 十一、排错对照表

按"现象"查。

### 传代码阶段（在**本机**执行时）

这是新手最容易卡住的一步，因为大多数报错**看起来和真正的原因毫无关系**。

| 现象 | 最可能的原因 | 怎么做 |
| --- | --- | --- |
| `bash: 172.40.3.224: No such file or directory` | 你把 IP 写成了 `<172.40.3.224>`，**`<` 和 `>` 被 bash 当成了"重定向"符号** | **去掉尖括号**。`<>` 只是"请替换这里"的示意符号，不是命令的一部分 |
| `rsync: command not found` | Git Bash **不自带** rsync | 本文档用的是 `tar + ssh`（第 3.2 节），不要照抄别的教程里的 rsync 命令 |
| `ssh: Could not resolve hostname` | 变量 `$SERVER` 没有值（多半是**重开了终端窗口**） | 重新执行 3.4 节那三行定义（`SERVER=...` / `LOCAL=...` / `REMOTE=...`） |
| `Permission denied (publickey,gssapi-keyex,...,password)` | 公钥没装到服务器上 | 执行 `ssh-copy-id root@$SERVER`（第 3.3 节），输一次服务器密码 |
| 传输过程中**卡住不动、也不报错** | 免密没配好，ssh 想问你密码，但键盘输入已被管道占用 | 回到第 3.3 节把免密配好，再重传 |
| `tar: ... Cannot stat: No such file or directory` | 忘了 `cd "$LOCAL"`，或路径写的是 Windows 格式（`C:\...`） | 先 `cd "$LOCAL"`；Git Bash 里路径要用 `/c/Users/...` 这种写法 |
| `tar (child): Cannot connect to C: resolve failed` | 给 `tar` 传了 `C:/Users/...` 形式的路径，`C:` 被当成了"远程主机名" | 改成 `/c/Users/...`（盘符小写、前面加斜杠）。详见 3.4 节那条警告 |
| 传完发现服务器上文件数上万 | `--exclude` 抄漏了，`node_modules` 被传上去了 | **先确认**：`ssh root@$SERVER 'du -sh $REMOTE/*/node_modules'`。确认这些确实只是依赖目录后，再单独删掉它们，然后照 3.4 节重新传一次 |

> 💡 **上表第一条值得单独记住**：`bash: xxx: No such file or directory`
> 这个错误 99% 的情况下和"文件"无关，而是**命令里出现了 bash 的特殊符号**。
> 除了尖括号 `<>`，还有 `&`、`;`、`|`、`(`、`)`、空格——
> 从网页复制命令时，最容易被这些符号坑到。
> 判断方法：看报错里冒号后面那个"文件名"是不是**你命令中的某个词**，
> 而且是个**不合法的路径**。如果是，就去找命令里混进了什么特殊符号。

### 启动阶段

| 现象 | 最可能的原因 | 怎么做 |
| --- | --- | --- |
| `docker compose up` 立刻报 `请在 server/.env 里设置站点对外地址` | `SITE_URL` 没填 | 编辑 `server/.env`，填上对外地址 |
| `docker: 'compose' is not a docker command` | Docker 版本太旧，没有 compose v2 | 按第四节重装 |
| 构建时卡在 `npm ci` 很久 | 网络问题（npm 源） | 国内主机确认 `.npmrc` 里是 npmmirror；海外主机把 `registry` 行删掉 |
| 构建时提示内存不足（`Killed`、`exit code 137`） | 内存不够（1G 主机常见） | 加 swap，或换 2G 以上主机 |
| `api` 一直 `starting` 不转 `healthy` | 后端启动失败 | `docker compose logs --tail=100 api` 看报错 |

> **补充：怎么看懂 `exit code 137`**
> 137 = 128 + 9，其中 9 是 `SIGKILL`（强制杀死信号）。
> 容器被强制杀死通常只有一个原因：**内存超了**，被系统的 OOM Killer 干掉了。
> 加 swap 的命令（在主机上执行）：
>
> ```bash
> fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
> echo '/swapfile none swap sw 0 0' >> /etc/fstab     # 让它开机也生效
> ```

| 现象 | 最可能的原因 | 怎么做 |
| --- | --- | --- |
| 首页 502 Bad Gateway | 前端容器没起来 / 崩了 | `docker compose logs client`；确认 `client` 是 `healthy` |

### 功能阶段

| 现象 | 最可能的原因 | 怎么做 |
| --- | --- | --- |
| 中文搜索特别慢（几秒才出结果） | 有人在库上跑过 `prisma db push`，**3 个搜索索引被删了** | 重跑建表脚本（幂等，可以放心执行）：`docker compose exec -T postgres psql -U blog -d blog < ../db/schema.sql`。详见 `server/README.md` 设计取舍第 1 条 |

| **恢复备份时报 `database "blog" is being accessed by other users`** | api 容器对 `blog` 库持有 4 条连接，`DROP DATABASE` 被挡住 | 先 `docker compose stop api client nginx`，或用 `drop database blog with (force);`（PG13+）。见 **10.4 节**警告框 |
| **恢复备份后数据"没变"或报主键冲突** | `pg_dump` 是增量式导出，**不会清空已有数据** | 必须先 `drop database` 再 `create database`，然后才灌 dump。见 **10.4 节** |
| **迁移后站点能打开，但所有链接都指向旧机器** | `server/.env` 的 `SITE_URL` 没改 | 改成新机地址后重启；sitemap/canonical/RSS 全靠它派生。见 **15.2 第 3 步** |

> **关于"中文搜索特别慢"这一条要多说一句**（这是本项目踩过的真实坑）：
>
> Prisma 有个 `db push` 命令，很多人习惯用它来"同步数据库结构"。
> 但在本项目里**绝对不能用**——它不认识 `schema.sql` 里的"函数索引"和"部分索引"，
> 执行时会**悄悄把这 3 个搜索索引删掉，而且不报任何错**：
>
> - `idx_articles_search_vector`（全文检索）
> - `idx_articles_title_trgm`（标题模糊匹配）
> - `idx_articles_summary_trgm`（摘要模糊匹配）
>
> 结果是中文搜索从"走索引"退化成"一行行翻全表"。数据量小的时候感觉不出来，
> 文章一多就慢得离谱，而且**日志里没有任何异常**。
>
> 所以：**表结构的唯一真实来源永远是 `db/schema.sql`**，
> `prisma/schema.prisma` 只用来生成类型安全的客户端代码。

## 十三、如果主机上不方便用 Docker

理论上可以不装 Docker，直接裸跑（把程序直接装在主机系统上）。
但**编排文件帮你做的那些事，你得自己做一遍**：

| 编排自动做的事 | 裸跑时要手动做什么 |
| --- | --- |
| 装好 PostgreSQL 18 并配好参数 | 自己装 PG，还要确保装了 `pg_trgm` 扩展（中文搜索依赖它） |
| 装好 Node 24 运行环境 | 自己装匹配版本的 Node |
| 进程崩了自动重启 | 用 `pm2` 或 systemd 写服务配置来守护两个 Node 进程 |
| 容器间用服务名互通 | 把 `nginx.conf` 里的 `upstream` 从服务名改成 `127.0.0.1:3000` / `127.0.0.1:3001` |
| 数据存卷、重建不丢 | 自己规划数据目录、上传目录，注意权限 |
| 开机自启 | 每个服务都要单独配 systemd |
| 环境变量隔离 | 自己用 shell 脚本或 systemd 的 `EnvironmentFile` 注入 |

**工作量明显更大，而且容易漏步骤，所以不建议。**

> **为什么文档和验证都是围绕 Docker 写的？**
> 因为"环境一致性"是部署里最省心的部分：Docker 保证了"本机跑通的版本组合"
> 原样搬到服务器上。裸跑的话，不同发行版的 Node 版本、PG 配置、
> 系统库版本都可能不同，出问题的地方会多很多。
>
> 如果你确实需要用裸装方案（比如公司的服务器政策不允许 Docker），

### 坑 1 ★★★ Docker 装好了却起不来：内核模块版本错配

**现象**：`systemctl start docker` 反复失败，`journalctl -u docker` 里真正的错误只有两行：

```
Warning: Extension addrtype revision 0 not supported, missing kernel module?
iptables v1.8.11 (nf_tables): RULE_APPEND failed: rule in chain PREROUTING
```

**根因链**（三步量出来的，不是猜的）：

1. 内核里**没有 `xt_addrtype.ko`**。Docker 的 bridge 网络驱动必须用
   `iptables -m addrtype ... -j DOCKER` 加 NAT 跳转规则；匹配器不可用 → 规则加不上
   → 网络控制器初始化失败 → 守护进程直接退出。
2. 为什么没有：`dnf install docker-ce` 会**顺带把内核升级**（依赖链带出了新内核的
   `kernel-modules-extra`），但**机器还在跑旧内核**，而 dnf 只给**新内核**装了模块包。
   精简安装的系统往往从来没装过 `kernel-modules` / `kernel-modules-extra`。
3. 为什么不能直接补：`dnf list available kernel-modules-extra-<旧内核版本>` 报
   `No matching Packages to list` —— **仓库只保留最新内核**，旧版本被顶掉了。

**量化判据**（这个数字最能说明问题）：

```bash
find /lib/modules/$(uname -r) -name '*.ko*' | wc -l       # 旧内核：1231 个模块
find /lib/modules/6.12.0-211.56.1.el10_2.0.1.x86_64 -name '*.ko*' | wc -l
#                                                            # 新内核：2413 个，差了近一倍
```

**解法 A（不重启，先用这个）**：从 Rocky 的**归档**里取与当前内核版本完全匹配的模块包。

```bash
KVER=$(uname -r)          # 例：6.12.0-124.8.1.el10_1.x86_64
BASE=https://mirrors.aliyun.com/rockylinux-vault/10.1/BaseOS/x86_64/os/Packages/k

# 先确认文件存在，能省一轮失败
curl -s -o /dev/null -w '%{http_code}\n' "$BASE/kernel-modules-$KVER.rpm"

dnf -y install "$BASE/kernel-modules-$KVER.rpm" "$BASE/kernel-modules-extra-$KVER.rpm"

modprobe xt_addrtype && modprobe br_netfilter      # 应无报错
systemctl restart docker
```

> ⚠️ **`uname -r` 的输出已经含 `.x86_64`**，拼 RPM 文件名时**不要再补一次**，
> 否则会拼成 `...el10_1.x86_64.x86_64.rpm` 得到 404。
> 路径里的 `/10.1/` 是系统版本，用 `cat /etc/redhat-release` 确认。

**解法 B（最标准，但要重启）**：重启进新内核，它自带全套模块。

```bash
grubby --default-kernel     # 确认默认启动项已指向新内核
reboot
```

重启前值得确认三件事：`/boot` 有足够空间、新内核的 `vmlinuz` 与 `initramfs` 都在、
**旧内核仍留在启动菜单里**（万一新内核起不来，还能在控制台选回去）。

> 💡 **解法 A 是一次性补丁，不是长期债**：下次重启会自动切到新内核，新内核自带全套模块，
> 那时旧内核的补丁包自然用不上了。顺手把模块加入开机自动加载，防止同类问题复发：
>
> ```bash
> cat > /etc/modules-load.d/docker.conf <<\EOF
> br_netfilter
> xt_addrtype
> overlay
> EOF
> ```

### 坑 2 ★★ SELinux 处于 Enforcing 时会拦住 bind mount

把**宿主机文件**挂进容器（而不是用具名卷）时，容器进程读不到该文件，
报错只有一句含糊的 `Permission denied`，非常难查。

**解法**：给这条挂载加 `,Z` 标签。

```yaml
volumes:
  - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro,Z      # ← 注意这个 ,Z
  - uploads:/var/www/uploads:ro                            # 具名卷不用管
```

- **具名卷（`pgdata` / `uploads`）不需要**，Docker 会自动打标签。
- 判断自己的主机是不是 Enforcing：执行 `getenforce`，输出 `Enforcing` 就是。
- 也可以用 `chcon -t container_file_t nginx.conf` 达到同样效果，
  但改在 compose 里更直观、更不容易被忘记。

### 坑 3 ★★★ PostgreSQL 18 的镜像改了数据目录布局

**现象**：`postgres` 容器反复重启，日志说：

```
Error: in 18+, these Docker images are configured to store database data in a
       format which is compatible with "pg_ctlcluster" ...
       Counter to that, there appears to be PostgreSQL data in:
         /var/lib/postgresql/data (unused mount/volume)
```

**别被 "appears to be PostgreSQL data" 这句话骗了** —— 卷**完全是空的**也会报。
它真正的意思是"你把卷挂在了 18 时代已经废弃的位置"。

**原因**：PostgreSQL 18 起，镜像的 `PGDATA` 变成了 `/var/lib/postgresql/18/docker`
（带大版本号的子目录，为的是 `pg_upgrade --link` 不跨挂载点），
官方建议把卷挂在**上一级** `/var/lib/postgresql`。

**解法**：改 compose 里的挂载点（**PG 16/17 及以前是挂 `/data` 的，网上老教程大多是旧的**）：

```yaml
volumes:
  - pgdata:/var/lib/postgresql          # ✅ 18 的正确挂法
  # - pgdata:/var/lib/postgresql/data   # ❌ 17 时代的写法，18 会拒绝启动
```

> 💡 好消息：**不用删卷、也不用重建数据库**，把挂载点改对再 `docker compose up -d` 即可
> （前提是还没建过表、卷还是空的 —— 首次部署正是这种情况）。
> 但如果你**已经在 17 上跑出数据了**，那必须用 `pg_upgrade` 迁移，不是改个路径能解决的。

### 坑 4 ★★ 前端容器必须设时区，否则日期会闪

`client/app/utils/format.ts` 的日期函数用的是 `d.getHours()` 这类
**依赖执行环境时区**的方法。容器默认 UTC，于是：

- 服务端渲染出 `2026-09-20 16:30`
- 浏览器按北京时间 hydration 成 `2026-09-21 00:30`
- 两边对不上 → Vue 报 **hydration mismatch**，日期先显示错的、再闪一下变对
- **前台每一篇文章都会命中**

**解法**：给前端容器固定时区（`docker-compose.yml` 的 `client` 服务里已经写好了）：

```yaml
environment:
  TZ: Asia/Shanghai
```

> 顺带看一眼主机时区：`date` 输出 `UTC` 而不是 `CST` 的话，用
> `timedatectl set-timezone Asia/Shanghai` 校正。

### 坑 5 ★★ 小内存主机的两个准备动作

| 动作 | 怎么做 | 为什么 |
| --- | --- | --- |
| **加 4G swap** | 见 6.1 节的代码块 | 1.7GB 内存 + 0 swap 时构建极可能被 OOM 杀掉 |
| **串行构建** | `build api` 再 `build client` | compose 默认并行，两个构建会抢内存 |

实测：加了 swap 后构建全程未触发 OOM，swap 峰值只用了约 **72 MB**。

## 十五、迁移到另一台服务器（换机或换机房）

> 本节的数据搬迁路径已于 **2026-09-20 在真机上完整预演通过**，
> 逐项比对数据见 15.4。建议先读 15.1 再动手。

### 15.1 先分清：要搬的是「数据」，不是「容器」

一套 compose 部署里，**代码可重建、镜像可重建、容器是临时的**。
真正**丢了就没了的**只有四样：

| 要搬的东西 | 在哪 | 丢了会怎样 |
| --- | --- | --- |
| **文章 / 用户 / 评论 / 分类 / 标签 / 站点设置** | `server_pgdata` 卷（PostgreSQL 数据） | **全站内容归零**，无法恢复 |
| **上传的图片** | `server_uploads` 卷 | 文章里的图片全变 404 |
| **`server/.env`** | 主机上的文件 | 密钥丢失 → 所有人掉线，且无法"还原" |
| 代码 | 你的本机目录 / 版本库 | 可重新传输，不算风险 |

**反过来，下面这些统统不用搬**（搬了反而可能出错）：

- `node_modules`、`dist`、`.output` —— 新机重新构建
- **Docker 镜像** —— 新机重新 `build`。镜像层**不能跨机直接拷**，架构/内核未必一致
- 容器本身 —— 新机 `up -d` 会重建

### 15.2 迁移五步

假设旧机 `OLD_IP`、新机 `NEW_IP`，两边目录都是 `/opt/blog`。

#### 第 0 步：先把新机「环境」备好（最容易漏，不做好后面全卡住）

新机**必须先完整走一遍**第四节（装 Docker）、6.1 节（串行构建 + swap）、
第十四节（内核模块 / SELinux / 时区），再谈迁移数据。重点：

- 内存 < 4G **一定要加 swap**，否则构建会 OOM
- SELinux 是 Enforcing 时，`nginx.conf` 的挂载**必须带 `,Z`**
- 配好 `registry-mirrors`，否则新机拉不下基础镜像

> **别跳过这一步。** 迁移失败大多不是数据搬错了，而是新机环境没准备好。

#### 第 1 步：在旧机上导出（几乎不停机）

```bash
# 旧机，在 /opt/blog/server 下执行
cd /opt/blog/server
mkdir -p /root/blog-backup

# ① 图片先打包 —— 要 exec 到「运行中」的 api 容器，所以必须放在停服务之前
docker compose exec -T api tar czf - -C /app/uploads . </dev/null > /root/blog-backup/uploads.tar.gz

# ② 短暂冻结写入，让「数据库」与「图片」处于同一时间点
docker compose stop api client nginx

# ③ 导出数据库
docker compose exec -T postgres pg_dump -U blog -d blog </dev/null > /root/blog-backup/blog.sql

# ④ 立刻恢复对外服务
docker compose start api client nginx

# ⑤ 配置也存一份（里面有密钥）
cp .env /root/blog-backup/env.backup
chmod 600 /root/blog-backup/env.backup

ls -l /root/blog-backup/
```

> `pg_dump` 本身是**一致性快照**，所以②严格来说不是必须的 ——
> 它只是为了让"图片包"和"数据库"严格对齐。博客这种写入量，
> 你也可以省掉②直接导出，代价是极小窗口内可能有新增数据没被包含。

#### 第 2 步：把「代码 + dump + 图片包」搬到新机

```bash
# 本机（不是服务器）—— 仍然用 tar + ssh，Git Bash 没有 rsync
cd /c/Users/lx/WorkBuddy/2026-09-17-17-12-31
tar czf - --exclude='node_modules' --exclude='.output' --exclude='.nuxt' \
  --exclude='dist' --exclude='.env' --exclude='.workbuddy' \
  . | ssh root@NEW_IP "mkdir -p /opt/blog && tar xzf - -C /opt/blog"

# 把旧机上那两个包拉过来，再推进新机
scp root@OLD_IP:/root/blog-backup/blog.sql \
    root@OLD_IP:/root/blog-backup/uploads.tar.gz \
    root@OLD_IP:/root/blog-backup/env.backup /tmp/
ssh root@NEW_IP "mkdir -p /root/blog-backup"
scp /tmp/blog.sql /tmp/uploads.tar.gz /tmp/env.backup root@NEW_IP:/root/blog-backup/
```

> 如果旧机与新机互通，让旧机直接推过去更省事：
> `ssh root@OLD_IP "scp /root/blog-backup/* root@NEW_IP:/root/blog-backup/"`

#### 第 3 步：在新机上填配置（**关键是改 `SITE_URL`**）

```bash
# 新机
cd /opt/blog/server
cp /root/blog-backup/env.backup .env
chmod 600 .env
vi .env          # ★ 只改 SITE_URL，改成新机的地址（不带末尾斜杠）
```

**`SITE_URL` 必须改。** sitemap、canonical、RSS、图片地址全靠它派生。
忘了改的症状是"站点能打开，但里面所有链接都指向旧机器" —— 极难发现。

> **JWT 密钥要不要一起换？**
>
> - **保留原密钥**（推荐，直接抄 `env.backup`）：所有人**不用重新登录**，无缝迁移。
> - **换新密钥**：所有人（包括你）都要重新登录。适合"旧机器不再可信"的场景。

#### 第 4 步：在新机建库 + 恢复数据

```bash
# 先只起数据库
docker compose up -d postgres
docker compose exec -T postgres pg_isready -U blog     # 等到出现 accepting connections

# 恢复数据库 —— dump 里带完整表结构，**不需要**再跑 schema.sql
docker compose exec -T postgres psql -U blog -d blog -v ON_ERROR_STOP=1 \
  < /root/blog-backup/blog.sql

# 恢复图片（先起 api，需要一个能 exec 的容器）
docker compose up -d api
docker compose cp /root/blog-backup/uploads.tar.gz api:/tmp/uploads.tar.gz
docker compose exec -T api tar xzf /tmp/uploads.tar.gz -C /app/uploads
docker compose exec -T api chown -R node:node /app/uploads   # ★ 别漏，否则应用可能写不进去
docker compose exec -T api rm -f /tmp/uploads.tar.gz
```

> ⚠️ **不要**再跑第七节的 `schema.sql`，也**不要**跑 `seed`。
> `pg_dump` 的产物**已经包含建表语句、索引、触发器、扩展和全部数据**
> （实测含 `CREATE EXTENSION` ×1、`CREATE TRIGGER` ×8）。
> 重跑 `schema.sql` 多余；重跑 `seed` 会**把分类再插一遍**。

#### 第 5 步：构建、启动、验收

```bash
docker compose build api        # 串行！小内存主机并行会 OOM
docker compose build client
docker compose up -d            # 4 个服务
docker compose ps               # 应全部 Up / healthy
```

按**第八节**验收，并**额外**确认新地址已经生效：

```bash
curl -s http://NEW_IP/sitemap.xml | head -20      # 里面的 URL 必须是新地址
curl -s http://NEW_IP/rss.xml | grep -o '<link>[^<]*</link>' | head -3
```

**① 先别急着关旧机。** 新机验收通过后，把旧机**停容器但保留数据**：

```bash
# 旧机
docker compose stop            # 只停容器，不动卷
```

⚠️ **绝对不要**在旧机上执行 `docker compose down -v` ——
那会删掉 `server_pgdata` 与 `server_uploads` 两个卷，
等于亲手烧掉唯一的回滚路径。

**② 切换流量。** 有域名就改 DNS 解析指向 `NEW_IP`（记得等 TTL 过期）；
纯 IP 访问就通知使用者换地址。

**③ 观察几天再善后。** 稳定运行一段时间后，再考虑清理旧机的卷。
在那之前，旧机就是你的"撤销键"。

**④ 确认新机开机自启。** `restart: unless-stopped` 已写在编排里，
但要确认 `systemctl enable --now docker` 在新机上也执行过（见 4.3 与 10.5）。
