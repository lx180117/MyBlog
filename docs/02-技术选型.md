# 博客平台 · 技术选型说明（Step 3）

> 日期：2026-09-17 ｜ 依据：《01-需求规格说明.md》v2
> 输入条件：**多作者**（开放注册 + 管理员审核）、**两级角色**、**已有服务器/内部环境**、技术栈由我推荐

## 1. 一句话结论

**Node.js 24 LTS + NestJS 11.2 + PostgreSQL 18 + Prisma + TypeScript**（后端），**Nuxt 4.5 + Nuxt UI v4**（前台 SSR），**Docker Compose + Nginx**（单机部署）。全部开源，**新增月成本 0 元**。

---

## 2. 为什么是这一套

选型时我按四条硬约束过滤：① 多作者 + 越权风险，框架必须有成熟鉴权机制；② 必须有 SSR，否则博客不被搜索引擎收录；③ 必须能自动产出标准 OpenAPI 文档（这是 Step 6 的输入）；④ 单台服务器能跑得动，不需要额外中间件。

| 决策点 | 选择 | 关键理由 |
| --- | --- | --- |
| 运行语言 | **TypeScript 一套到底** | 前后端同语言，一个人维护成本最低；类型在前后端间直接复用 |
| 运行时 | **Node.js 24（Active LTS）** | 当前 Active LTS，支持到 2028-04。注意：Node 20 已 EOL，Node 22 进入维护期，Node 26 还没转 LTS，**24 是唯一稳妥选项** |
| 后端框架 | **NestJS 11.2.x** | 模块化 + 依赖注入 + Guard 守卫，天然适配「作者只能改自己的文章」这类越权校验；`@nestjs/swagger` 用装饰器直接产出 OpenAPI 3，**Step 6 零成本衔接** |
| 不用 NestJS 12 | — | v12.0.0 于 2026-08-27 才发布，带来 ESM 全面迁移等破坏性变更，上线仅三周，**不适合生产** |
| ORM / 迁移 | **Prisma** | schema 即模型，`prisma migrate` 直接产出 SQL DDL —— **Step 4 可以同步产出数据库脚本，一举两得** |
| 数据库 | **PostgreSQL 18** | ① 原生全文检索（tsvector + GIN 索引）直接满足搜索，**省掉一个 Elasticsearch**；② JSONB 存站点配置，`site_setting` 表可以很灵活；③ 18 为当前最新主版本（社区支持至 2030+） |
| 缓存（可选） | **Redis 7+** | 存 Refresh Token 黑名单、登录失败计数、评论频率限流。**v1 可用进程内存替代，不必强上** |
| 密码哈希 | **argon2** | 抗 GPU 爆破强于 bcrypt，NestJS 生态有现成封装 |
| 会话 | **JWT 双 Token** | Access 15 分钟 + Refresh 7 天；支持后台踢人（黑名单） |
| 前台框架 | **Nuxt 4.5.x（SSR）** | 博客必须被收录，SPA 不行。**注意 Nuxt 3 已于 2026-07-31 EOL，只能用 4** |
| 前台 UI | **Nuxt UI v4** | 自 2025-09 起完全免费，110+ 组件，自带暗黑模式与无障碍支持，省掉自研主题成本 |
| 后台 UI | **Element Plus** | 后台是表格 + 表单密集场景，Element Plus 的 Table / Form 组件比通用组件库更省事 |
| Markdown | **markdown-it + Shiki + DOMPurify** | 渲染 + 代码高亮 + 输出转义（防 XSS，对应非功能安全要求） |
| 图片存储 | **本地目录 + 存储抽象层** | 先在服务器本地存，接口抽象成 `StorageService`，日后换 OSS/COS 只改一个实现类 |
| 反向代理 | **Nginx** | TLS 终止、静态资源直出、`/api/*` 转发到后端、SSR 进程反代 |
| 部署 | **Docker Compose** | 4 个容器一键起停（web / api / postgres / nginx），内部环境交付简单；也便于日后迁移 |
| 备份 | **pg_dump 每日定时 + 上传目录同步** | 对应非功能「数据可备份」 |

## 3. 部署架构

```
浏览器 / 搜索引擎爬虫
        │  HTTPS 443
        ▼
┌─ Docker Compose（单台服务器）──────────────────┐
│   Nginx  ·  TLS 终止 · 静态资源 · /api 转发     │
│         │                    │                 │
│         ▼                    ▼                 │
│   Nuxt 4 SSR 前台      NestJS API              │
│   （SEO / 暗黑模式）    （REST / JWT / Swagger） │
│                              │                 │
│   ────────────── 内部网络总线 ──────────────    │
│        ▼              ▼            ▼           │
│   PostgreSQL 18    Redis（可选）  本地上传目录   │
└────────────────────────────────────────────────┘
```

### 关键路径说明

- 前台请求 `/`、`/article/:id` → 由 **Nuxt SSR** 直接渲染成 HTML，爬虫拿到的是完整内容。
- 后台请求 `/admin/*` → 关闭 SSR，走 SPA 模式，只在内网或登录后使用。
- 接口请求 `/api/*` → Nginx 转发到 **NestJS API**，Nuxt 在服务端渲染时也通过内网调用同一套 API。
- Swagger UI 暴露在 `/api-docs`，机器可读的 `openapi.json` 在 `/api-docs-json` —— **这就是 Step 6 的输入文件**。

## 6. 这一套如何衔接后续步骤

| 后续步骤 | 衔接方式 |
| --- | --- |
| Step 4 · DDL 数据库模型 | Prisma schema 即模型定义，`prisma migrate dev --create-only` 直接产出标准 PostgreSQL DDL 脚本 |
| Step 5 · 后端 + Swagger | NestJS 启动后 `/api-docs-json` 就是标准 `openapi.json`，无需手写文档 |
| Step 6 · 前端生成 | 把 `openapi.json` 喂给生成器（或 AI），产出类型安全的 API 调用层与页面骨架 |
| Step 7 · 墨刀原型回流 | 前台在 Nuxt 中按页面组件拆分（`pages/`），原型改造只动 UI 层，不碰接口层 |

## 7. 风险与替换预案

| 风险 | 预案 |
| --- | --- |
| 单位内网有「只能用 Java」的硬性规定 | 换 **Spring Boot 4.0.6 + Java 17+（Spring Framework 7）+ MyBatis-Plus + MySQL 8**。架构、表结构、接口设计完全不变，只换实现语言，DDL 基本可直接复用 |
| 服务器已有 MySQL 且不允许装 PostgreSQL | 换 MySQL 8，全文检索退化为 `FULLTEXT` + ngram 分词器；Prisma 换 provider 即可，schema 改动很小 |
| 内网不允许装 Docker | 改用 systemd + Nginx 裸机部署，Node 进程用 systemd 守护，前端用 `node .output/server/index.mjs` 直接跑 |
| 服务器内存 < 2GB | 去掉 Redis（改用进程内存），把 Node 堆上限压到 256MB，前台 SSR 改混合渲染（部分页面预渲染） |
| 不需要被搜索引擎收录 | 前台可退化为纯 SPA，省掉 SSR 的复杂度与内存开销 |
| 日后访问量涨到万级 PV | PostgreSQL 全文检索换成 Meilisearch（单二进制、内存占用小），其余层不动 |
